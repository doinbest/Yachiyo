# 张大头风格 STM32 代码规范与 AI 提示词

## 1. 文档用途

本文总结张大头闭环步进电机 `Emm_V5` 官方例程中值得保留的代码风格，以及本项目在多轮修改中形成的编码要求。

适用范围：

- STM32 HAL 库裸机工程；
- 电机、传感器、按键和串口等硬件模块；
- 简单任务程序和小车运动控制；
- 交给 AI 编写、修改或审查嵌入式 C 代码时作为提示词。

目标不是逐字照搬官方代码，而是保留其“函数用途一眼可见、命令结构容易对照手册、调用流程短而清楚”的优点，同时修正返回值说明、错误处理和模块边界等不严谨之处。

## 协作与实施约定（2026-09-21）

用户提出需求、修改建议、关键取舍并进行实物验收；Codex 默认完成方案、全部代码、集成、测试和文档。说明原理是为了帮助理解，不要求用户手动复制示例或亲自集成。

明确的实施请求允许同步维护相关实现、接口、工程文件清单、测试和文档；分析/审查请求先给结论。鼓励主动提出适合当前目标的改进，并核查优秀开源实现的来源、许可证及硬件适配性，记录实际借鉴；不扩展成无关重构。硬件操作仍需明确意图及完整参数。详细规则以根目录 AGENTS.md 为准。

## 2. 总体风格

代码应优先满足以下要求：

1. **通俗易懂**：函数名称直接描述动作，不使用没有必要的长单词和学术词汇。
2. **调用链短**：上层函数应能直接找到实际执行动作的位置，避免多层空壳封装。
3. **一函数一任务**：初始化、读取、计算、发送和业务判断分别放在职责清楚的函数中。
4. **参数可追踪**：参数必须写明含义、单位、范围、正负方向和特殊取值。
5. **协议可对照**：通信命令应按照协议字节顺序装载，并在每个字节旁标明用途。
6. **先简单验证**：优先采用官方例程或最简单的 HAL 调用验证硬件，再根据需要引入中断、DMA、状态机或 RTOS。
7. **不破坏生成代码**：CubeMX 生成文件只在 `USER CODE` 区域添加必要调用，自研功能放入独立目录。
8. **结论必须验证**：修改后至少完成编译；涉及硬件时给出最小上板测试方法和观察点。

## 3. 工程目录职责

当前项目采用以下分层：

```text
Code/template/
├─ Core/       CubeMX 生成的初始化、中断入口和 main.c
├─ Hardware/   电机、按键、传感器、通信模块等硬件功能
├─ App/        底盘、机械臂、视觉、控制台和显示业务
├─ System/     delay 等系统公共功能
└─ Drivers/    STM32 HAL 和 CMSIS 第三方代码
```

约定：

- `Hardware` 负责“某个硬件怎样工作”，不决定整车业务。
- `App` 负责“什么时候调用哪些硬件动作”。
- `System` 只放与具体业务无关的公共功能。
- `Core` 保持 CubeMX 结构，`main.c` 只保留清楚的初始化顺序和主循环入口。
- 官方提供的 `Emm_V5.c/.h` 保留原接口名称，方便与官方手册和示例逐行对照。
- 不为追求所谓通用性，额外建立没有实际职责的 `Manager`、`Service`、`Adapter` 或多层回调。

## 4. 函数命名规则

### 4.1 基本格式

优先使用：

```text
模块_对象_动作()
模块_动作()
```

名称中的最后一个词尽量表达动作，例如：

- `Init`：初始化；
- `Read`：读取；
- `Get`：取得结果；
- `Set`：设置参数；
- `Calc`：计算；
- `Control`：执行控制；
- `Process`：在主循环中周期处理；
- `Start`、`Stop`、`Reset`：启动、停止、复位。

### 4.2 推荐示例

```c
void Key_Init(void);
void Key_Scan(void);
KeyEvent_t Key_Get_Press_Event(void);

void Chassis_Key_Init(void);
void Chassis_Key_Process(void);

bool Mecanum_Move_Control(float forward_mm,
                          float left_mm,
                          float yaw_rad);

bool Mecanum_Wheel_Speed_Calc(float forward_mm_s,
                              float left_mm_s,
                              float yaw_rad_s,
                              float wheel_mm_s[4]);

uint32_t Mecanum_Distance_To_Pulse(float distance_mm);
bool Delay_Time_Is_Up(uint32_t start_tick, uint32_t interval_ms);
```

### 4.3 不推荐示例

```c
MecanumChassis_InverseKinematics();
MecanumChassis_DistanceToCommandPulses();
ChassisKeyTestProcessHandler();
MotorUniversalServiceExecute();
```

主要问题：

- 单词过长，调用处难以快速阅读；
- 使用偏学术的 `InverseKinematics`，却没有直接说明函数输入和输出；
- 把多个单词连成类似 C++ 类名，不符合本项目直观的 C 风格；
- `Handler`、`Manager`、`Service` 等词没有说明实际动作。

专业概念可以保留在注释中。例如函数名使用 `Mecanum_Wheel_Speed_Calc()`，注释再说明“该计算属于麦轮逆运动学解算”。

### 4.4 官方接口名称

张大头官方接口保持原名，不自行翻译或二次包装：

```c
Emm_V5_En_Control();
Emm_V5_Vel_Control();
Emm_V5_Pos_Control();
Emm_V5_Stop_Now();
Emm_V5_Synchronous_motion();
```

这样做便于：

- 搜索官方手册；
- 对照官方示例；
- 检查功能码和参数顺序；
- 向厂家技术支持描述问题。

只有当底层通信介质发生变化时，才替换命令最终发送位置，不改变上层官方命令编码接口。

### 4.5 参数和变量命名

- 名称应包含单位：`distance_mm`、`speed_rpm`、`time_ms`、`yaw_rad`。
- 数组应说明内容：`wheel_speed`、`motor_address`，避免 `data1`、`buf2`。
- 状态变量应说明状态：`chassis_is_moving`、`pending_event`。
- 循环变量可以使用 `index`、`wheel`；协议装载时可以使用简单的 `i`、`j`，但作用域必须短。
- 宏使用全大写和下划线：`CHASSIS_WHEEL_DIAMETER_MM`。
- 测试程序的文件名可以包含 `test`，但正常业务入口不必写成 `Chassis_Key_Test_Process()`；使用 `Chassis_Key_Process()` 即可。

## 5. 注释格式

### 5.1 功能分区

参考官方例程，用明显的分区标题组织同类函数：

```c
/**********************************************************
*** 运动控制命令
**********************************************************/
```

标题应描述本组代码的实际职责，例如：

- `按键初始化`
- `按键扫描与消抖`
- `距离与电机脉冲换算`
- `四电机同步位置控制`
- `串口命令发送`

### 5.2 函数注释

公开函数和重要静态函数均使用完整注释：

```c
/**
  * @brief    控制四轮按给定车体相对位移同步运动
  * @param    forward_mm ：车体前后位移，向前为正，单位 mm
  * @param    left_mm    ：车体左右位移，向左为正，单位 mm
  * @param    yaw_rad    ：车体旋转角度，逆时针为正，单位 rad
  * @retval   true  ：四台电机命令和同步触发命令已经发出
  * @retval   false ：参数无效，没有发送运动命令
  * @note     每台电机先使用 snF=true 缓存命令，最后由地址0广播触发
  */
bool Mecanum_Move_Control(float forward_mm,
                          float left_mm,
                          float yaw_rad);
```

注释要求：

- `@brief` 使用通俗中文，直接写函数做什么。
- 每个参数都必须有 `@param`。
- 参数必须写清单位、范围、方向和特殊值。
- 非 `void` 函数应列出每种关键返回值。
- `void` 函数写 `@retval 无`。
- 前置条件、执行方式、协议返回帧或风险写入 `@note`、`@pre` 或 `@warning`。

官方代码有时把“驱动器返回帧”写在 `void` 函数的 `@retval` 中。项目中应改成更准确的写法：

```c
/**
  * @brief    触发编码器校准
  * @param    addr ：电机地址
  * @retval   无
  * @note     驱动器正常返回：地址 + 功能码 + 命令状态 + 校验字节
  */
```

### 5.3 函数内部注释

内部注释重点解释“为什么”和“硬件含义”，不要逐字翻译 C 语句。

推荐：

```c
/* snF=true：先缓存位置命令，四台电机此时都不立即运动。 */
Emm_V5_Pos_Control(addr, dir, vel, acc, pulse, 0U, true);

/* 地址0为广播地址，统一触发所有已经缓存命令的电机。 */
Emm_V5_Synchronous_motion(0U);
```

不推荐：

```c
/* 调用函数。 */
Emm_V5_Synchronous_motion(0U);

/* i加1。 */
i++;
```

### 5.4 协议字节注释

电机通信命令应保留官方例程这种直观写法：

```c
cmd[0]  = addr;                  /* 电机地址 */
cmd[1]  = 0xFD;                  /* 位置控制功能码 */
cmd[2]  = dir;                   /* 运动方向 */
cmd[3]  = (uint8_t)(vel >> 8);   /* 速度高8位 */
cmd[4]  = (uint8_t)(vel);        /* 速度低8位 */
cmd[5]  = acc;                   /* 加速度，0表示直接启动 */
cmd[12] = 0x6B;                  /* 固定校验字节 */
```

不要把一整条协议命令压缩成难以核对的复合表达式。

## 6. 函数设计要求

### 6.1 一个函数只完成一个明确任务

推荐拆分：

```text
Key_Scan()                  读取并消抖按键
Key_Get_Press_Event()       取得一次按键事件
Mecanum_Distance_To_Pulse() 距离换算
Mecanum_Move_Control()      生成并发送四轮命令
Chassis_Key_Process()       决定按键触发哪种运动
```

不要在一个函数中同时完成按键扫描、运动学计算、协议组包、串口接收解析和显示刷新。

### 6.2 区分公开接口和内部函数

- 其他文件需要调用的函数放在 `.h` 中声明。
- 只在本文件使用的辅助函数声明为 `static`。
- 不为只有一行转发代码的函数增加新的公开接口。
- 头文件负责告诉调用者“如何使用”；`.c` 文件负责说明“如何实现”。

### 6.3 控制流程应直接可见

四电机同步控制的推荐流程：

```text
计算四轮距离
  → 分别向 ID 1、2、3、4 发送位置命令，snF=true
  → 每条命令之间保留经过验证的短延时
  → 向地址0发送同步触发命令
```

这组命令只在动作发生时发送一次，不应无条件放在 `while(1)` 中持续重复发送。

### 6.4 不过早增加复杂机制

- 官方轮询示例能够验证硬件时，先使用轮询。
- 确认通信和协议正确后，再根据实时性决定是否使用中断或 DMA。
- 中断只做必要的数据搬运、清标志或置事件，不在中断内执行复杂运动控制。
- 如果使用 DMA，必须说明发送缓冲区生命周期、忙状态、完成条件和超时处理。
- 不以“架构更高级”为理由增加难以单步跟踪的回调链。

## 7. STM32 HAL 与 CubeMX 约定

1. 当前工程使用 STM32 HAL，查阅资料和代码时不得混用标准外设库接口。
2. 外设句柄、GPIO 复用、DMA 映射和中断入口以当前芯片、CubeMX 配置及对应 HAL 源码为准。
3. `MX_GPIO_Init()`、`MX_UART5_Init()` 等函数由 CubeMX 管理。
4. 自研初始化必须放在所有依赖的 `MX_*_Init()` 之后。
5. `main.c` 中仅保留清楚的初始化和主循环调用，例如：

```c
MX_GPIO_Init();
MX_DMA_Init();
MX_UART5_Init();

HAL_Delay(500U);
Chassis_Key_Init();

while (1)
{
  Chassis_Key_Process();
}
```

6. 除非明确要求，不修改 HAL、CMSIS 等第三方源文件。
7. CubeMX 重新生成代码前，检查 `USER CODE` 区域和工程差异。

## 8. 配置参数约定

可调整的机械、电机和测试参数集中放入配置头文件，不散落在业务代码中：

```c
#define CHASSIS_WHEEL_DIAMETER_MM          100.0f
#define CHASSIS_MOTOR_TO_WHEEL_RATIO       1.0f
#define CHASSIS_COMMAND_PULSES_PER_REV      3200U
#define CHASSIS_ENCODER_COUNTS_PER_REV      16384U
#define CHASSIS_TEST_SPEED_RPM              1000U
#define CHASSIS_UART_COMMAND_INTERVAL_MS    10U
```

每个参数应注明：

- 来源是手册、网页、实测还是临时假设；
- 单位；
- 修改后会影响什么；
- 是否需要重新标定或上板验证。

不得把未经确认的轮径、减速比、编码器线数或方向参数描述为最终值。

## 9. 修改和验证流程

每次修改遵循：

1. 阅读用户提供的手册、官方示例和当前工程代码。
2. 区分官方事实、代码推断和待上板验证的假设。
3. 检查 Git 工作区，保留用户已有修改。
4. 将需求拆成可独立验证的小步骤，在已授权范围内连续实现。
5. 同步修改 `.c` 定义、`.h` 声明和全部调用位置。
6. 搜索旧名称，确保没有遗漏调用。
7. 使用当前 Keil Target 全量编译。
8. 先报告第一个编译错误，不用后续错误淹没根因。
9. 编译成功后说明错误数、警告数和日志位置。
10. 没有明确授权时不烧录、不复位硬件、不发送实际控制命令。

硬件测试应从最小现象开始：

```text
外设初始化是否完成
  → 命令函数是否执行
  → 实际发送字节是否正确
  → 电平、波特率和接线是否正确
  → 驱动器是否返回数据
  → 单电机是否动作
  → 最后再测试多电机同步和底盘组合动作
```

## 10. 可直接复用的完整 AI 提示词

下面内容可以复制到其他 STM32 项目中，并替换方括号中的项目资料。

```text
你正在协助我编写一个基于 STM32 HAL 库的嵌入式 C 工程。

项目目标：
[填写本轮要实现的具体功能]

硬件和接口：
[填写 MCU、引脚、外设、通信参数和模块型号]

参考资料：
[填写用户手册、官方示例、参考手册和工程路径]

请严格遵循以下编码要求：

1. 先阅读我提供的手册、官方示例和当前工程代码，再提出或实施修改。
2. STM32 外设代码只使用当前工程的 HAL 库，不得混入标准外设库写法。
3. 参考张大头 Emm_V5 例程的清晰风格：函数用途直接、协议字节逐项装载、参数注释完整、调用流程短。
4. 不要机械照搬官方代码中的无限等待、错误返回值描述或其他不严谨写法；应结合当前工程进行安全修正。
5. 自研函数优先采用“模块_对象_动作”或“模块_动作”命名，例如：
   - Key_Init()
   - Key_Get_Press_Event()
   - Mecanum_Move_Control()
   - Mecanum_Distance_To_Pulse()
6. 避免 InverseKinematics、UniversalManager、ServiceHandler 等过长或不直观的函数名称；专业术语放在中文注释中解释。
7. 官方提供的函数名称保持不变，例如 Emm_V5_Pos_Control()，方便对照手册。
8. 函数名不要无意义地添加 Test、Manager、Service、Handler 等后缀。
9. 参数名称尽量包含单位，例如 distance_mm、speed_rpm、time_ms、yaw_rad。
10. 一个函数只完成一个明确任务；只在当前文件使用的辅助函数必须声明为 static。
11. 不增加没有实际价值的包装层、复杂回调、通用事件总线或深层状态机。
12. 新功能先用最简单、可单步调试的方式验证；只有确有必要时才引入中断、DMA 或 RTOS。
13. 中断函数只处理必要的硬件事件，不在中断中执行复杂业务控制。
14. CubeMX 生成代码尽量不改；自研代码放到 Hardware、App 或 System，main.c 只保留初始化和主循环入口。
15. 使用以下功能分区格式：

   /**********************************************************
   *** 功能名称
   **********************************************************/

16. 每个公开函数和重要静态函数必须提供：
   - @brief：用通俗中文说明功能；
   - @param：说明每个参数的含义、单位、范围和方向；
   - @retval：说明每种返回值，void 函数写“无”；
   - @note：说明前置条件、调用位置、同步标志、协议返回或注意事项。
17. 函数内部注释解释硬件含义、公式和设计原因，不写“i 加1”之类无价值注释。
18. 通信协议代码应按字节顺序展开，并在每个字节后注明地址、功能码、参数高低位和校验字节。
19. 可调参数集中放在配置头文件中，并注明来源、单位和待验证项。
20. 保留当前工作区中与任务无关的用户修改，不覆盖、不删除。
21. 修改时同步更新 .c、.h、main.c 和所有调用位置，并搜索确认旧名称没有残留。
22. 修改后使用当前工程的 Keil Target 进行全量编译；报告错误数、警告数和日志路径。
23. 未经我明确授权，不烧录固件、不复位硬件、不发送真实控制命令。

开始修改前，请先用简短文字说明：
- 你理解的本轮目标；
- 将修改哪些文件；
- 哪些内容来自官方资料，哪些属于待上板验证的假设。

完成后请告诉我：
- 实际修改内容；
- main.c 中新增或修改的调用；
- 编译结果；
- 最小上板测试步骤；
- 尚未验证的风险。
```

## 11. 精简版提示词
