# 地图遥测 COM23 实测定位

## 范围

作者明确授权通过串口采集，确认 COM23、DL-20 无线模块。参数沿用当前工程 USART1：115200、8N1、无硬件流控。作者说明车辆在起始点；本轮没有设置原点，也没有发送任何运动、使能、复位、标定、参数保存命令。

串口扫描使用 serial skill。采集使用 Python/pyserial 直接读取原始字节，不经过网页。仅发送 `info`、`chassis stream on 9120501`、`chassis stream off`。每轮结束关闭遥测、再次读取 info，并关闭串口句柄。没有改动或烧录固件。

## 结果

| 对照 | 结果 | 说明 |
| --- | --- | --- |
| 遥测开启前 info | 回复完整 | 基本命令和无线往返能工作 |
| 连续开启约 12 秒 | 识别到 21 条 @CHASSIS 行，21 条 JSON 均无效 | 丢失的不只是整帧，帧内部字段和引号也缺失 |
| 关闭遥测后 info | 回复完整 | 停止持续输出后，短回复恢复正常 |
| 开启约 63 ms 后发送关闭 | 收到 1 条完整状态 JSON | 启动配置和相关回复仍残缺，不能判定地图恢复；不能宣称所有长帧都无法传输 |
| 固件格式化模块 + 实际 ConsoleTx，主机逐字节异步发送模型 | 16 条 JSON 均有效，发送丢弃计数为 0 | 未复现缓冲区被下一帧覆盖；这是主机模型，不等于测得 MCU TX 引脚波形 |

## 可以确定的结论

1. 网页之外直接读取 COM23 也收到残缺 JSON，网页 JSON.parse 报错合理。不是地图参数或原点设置造成格式错误。
2. 连续遥测配置为每 200 ms 输出一次，一条状态约 1 KB，距离任务状态可能更长。按原 UART 波特率可发送，并不等于无线链路在同样节奏下也能保持完整。
3. 现有 ConsoleTx 保证正在发送的缓冲区不被覆盖，但对遥测调用一次 HAL_UART_Transmit_IT 连续发出整条长记录；普通回复按至多 256 字节拆块，也没有无线传输所需的节奏控制。
4. `dropped=0` 只覆盖 MCU 软件发送管理记录的丢弃，不覆盖无线或电脑接收链路中的丢失。
5. 格式错误和定位不可用是两个问题。完整状态帧仍显示原点、四轮反馈未就绪；修好传输后，地图也不能把无效反馈当作实车坐标。

## 尚不能断言的部分

未同步采集 MCU PA9 引脚上的原始输出，也未核对 DL-20 当前空中速率、缓存和分包配置，因此不能仅凭 COM23 结果把根因唯一归到某个无线硬件缓存。已观察到的是：短查询正常，持续大报文损坏，停止输出后恢复；最优先处理长报文发送节奏与链路承载能力之间的不匹配。

## 建议的修改边界

- MCU 端给 USART1 长输出增加非阻塞分段与间隔；块长、间隔和总速率需可配置并通过实测选择，不只依靠串口 115200 推断。
- 配置与运行状态分开安排，启动时避免配置、回显、确认和状态集中突发；运行状态去除不必要的重复常量、精度和字段。
- 未发送的旧状态可替换；已经开始发送的 JSON 必须完整结束，不能在其中插入普通命令回复。需要为停止等命令保留合理的链路响应时间。
- 如使用低速遥测，网页超时和轨迹分段规则需与新周期匹配，不能仅把固件从 5 Hz 降到 1 Hz、仍保留网页 600 ms 超时。MCU 的电机反馈新鲜度和安全停车阈值不随网页降低频率而放宽。
- 关闭遥测应取消待发送状态；已开始发送的记录需要明确结束策略。网页不能以解析失败代替关闭 MCU 遥测。
- 验证从连续原始采集开始：配置完整、状态完整、JSON 合法率、实际刷新间隔、查询往返延迟、关闭后停止输出，然后才验收网页显示。

本轮完成串口实测和原因范围收敛，未宣称地图问题已经修复。
