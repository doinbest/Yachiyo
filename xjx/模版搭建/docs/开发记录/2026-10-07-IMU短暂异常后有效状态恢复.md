# IMU 短暂异常后有效状态恢复

用户报告 `grab ring align` 被拒绝，任务空闲且 `reason=imu_invalid`，要求从代码修复。

源码确认：`GrabTask.c` 启动协同对准前读取 `HWT101_Cal_ControlAngleGet`。旧逻辑在运行期发现累计 I2C 错误数与验证时基线不同、数据不新鲜或采样间隔超过 300 ms 后，将 `control_valid` 置 false；Process 只处理有效状态，getter 又先拒绝无效状态，形成没有恢复出口的锁死。驱动自身重新探测恢复后仍不能恢复控制资格。现有任务日志不能确定现场最初是 I2C 错误还是采样超时；本次修复的是已经由测试复现的永久锁死路径。

修改 `hwt101_calibration.c/.h`：统一主循环和角度读取的状态维护；运行期错误计数与严格校准验证基线分离；已完成成功验证且模式正常时，暂停后连续观察两帧新鲜有效角度恢复。新增错误会清空恢复进度，缓存重复读取不累计；新鲜度与采样间隔仍采用原 300 ms 阈值。正常 getter 同时更新接受的时间戳，避免主循环未及时维护导致后续误超时。

不重写零偏、不归零、不发送 SAVE，不清累计 I2C 错误，不改变地图原点、抓取参考和运动任务状态。仍拒绝正在标定、未验证、验证失败、取消、仅归零、模式未确认和原生保存失败。运行中的任务仍沿现有流程处理 IMU 不可用，不自动恢复已故障或停止的动作；数据恢复后用户可再次启动任务。

验证：先新增故障恢复测试，在旧代码的恢复断言处失败，再修改实现。覆盖 getter/Process 两个入口、两帧恢复、同帧重复读取、恢复期新增错误、持续不可用、非有限角度、过期数据、采样间隔、取消/失败/仅归零/保存失败及时间戳回绕。主机测试与 Keil 构建结果见 `.embeddedskills/tests/host-tests.log` 和 `.embeddedskills/build/template-template-build.log`。

本次只修改代码、测试和文档，没有发送车端串口命令或烧录。固件需要下载到 F407 后验证：上电静止验证通过，先确认 `imu status` 的 `control_ready=1`；短暂数据异常期间为 0，恢复后回到 1，再次启动圆环对准。代码修复不代表现场 I2C 干扰或主循环超时原因已经排除。
