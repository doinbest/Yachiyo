# 实车监控三圈判障与结果同步提速

日期：2026-10-06。范围为正式 `#map/monitor`；备用 F1 雷达建图页不改。COM14、USART1 115200/8N1、USART2 921600、已验证安装转换和判障/规划核心保持不变。

## 本轮需求与实现

- 减少地图、路径逐页请求的无线往返，采集完成后尽快显示完整障碍与路径。
- 正式按钮改为“扫描3圈并规划”：`radar scan lower 3` 或 `upper 3`。一次启动雷达，连续三个有效完整圈，同一冻结配置，第三圈后统一发布并规划。
- 每圈仍用原完整点云/全点流式判障、现有场边规则与工位保护；三圈有效障碍 mask 取并集，任一圈命中就保留。不是三次命中才认可，也不是三圈不足阈值点数相加后重新判障。
- counts 累计、evidence 并集用于诊断；按需完整 cloud 只保留最后一圈，网页安装详情明确标注。新一轮重新累计，移走的物体不会永久残留；失败/停止保留上次完整历史图。
- 一个 `radar result <plan>` 回传 map/path，`result_end` 报告实际页数。网页收到全部同身份页面即可完成，仅缺页 fetch 补读。旧单页接口保留。
- 根据冻结数值实际位宽预算 counts 容量，路线元数据只在第0页；路径四字段整数坐标原样保留。常见地图2页、18点路线3页，长路线页数仍随数据变化。
- USART1 不恢复全局30ms分块等待。实测无间距连续突发会造成无线坏页，因此仅结果流以100ms非阻塞页面调度发送；主循环、停车优先回复与其他通信照常运行。

## 定位到的主要延迟

原逐页请求：一次正常样本9次请求（地图3页、路径6页），结果下载约4407ms，总等待8424ms。仅取消逐页往返、直接突发，仍会因坏页补传延迟；此外旧客户端在后台重复下载造成竞争。

测试时刷新遗留内置浏览器仍发现另一旧客户端请求。重启已精确确认的本地8765服务，应用新后端；测速使用既有准备独占接口隔离其他页面的只读请求，扫描发出后获取、完成后释放，未新增生产互锁。最终日志的 allTx 与测试程序 wires 一致，无其他页面下载竞争。

## DAPLink / COM14 实测

Keil Target `template`：0错误、0警告，Flash 195500B、RAM 112108B。DAPLink/OpenOCD 对生成 HEX 烧录并 verify 成功；测试复位时在已确认的 `GrabTask_BootHomeStart` 入口跳过该次启动回零，随后恢复正常主循环，仅为避免验证期间机械臂自动运动，未改源码启动逻辑。

最终三组均采完3圈、一次请求收齐，无缺页补传。网页与固件公共身份、25格计数完整校验通过，设备有序路线与本地相同 C 核心逐点一致。

## 网页按钮验收与重新上电恢复

新版按钮与三圈状态已载入，点击真实按钮发送 `radar scan lower 3`。但该次雷达没有新的测距圈，10秒窗口结束0/3；COM14继续正常收到STM32状态。只读诊断：`alarm=20804,last_alarm=256,packets=404,overflow=0,tx_errors=0,uart_errors=0,rx_ready=true`；这里仅记录原始报警码0x0100，不推断其具体含义或归咎于网页算法。已请求用户将雷达及车端串口模块重新上电后继续网页实测，旧完整地图保留。此前三组真实串口测速成功不等于这一次网页验收成功。

用户重新上电后，COM14 连接随模块重启断开；在内置浏览器显式重新连接 COM14，再点击“扫描3圈并规划”。实际发送 `radar scan lower 3`，设备 session13 / scan1 / map1 / plan1，三圈完整采集成功。一次 `radar result 1` 收齐地图2页及路径3页，无缺页补传；总等待4168ms，收到 ready 后下载689ms。地图冻结元数据 c=3，25格 counts 完整，网页显示“已采集3/3圈”、2个扫描障碍格、18个规划坐标点、路线可达；浏览器 error/warn 日志为空。本次实际网页按钮验收成功，未发送底盘/机械臂运动命令。
