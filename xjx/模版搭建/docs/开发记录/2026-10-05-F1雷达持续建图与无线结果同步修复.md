# F1雷达持续建图与无线结果同步修复（2026-10-05）

## 范围与定位依据

用户授权修改STM32和网页，解决雷达页“不显示障碍/路线”的问题；本轮仅主机剖面 `f1_host`、雷达页、必要的桥接握手、测试与文档。实车监控、离线算法、实车雷达建图、运动、IOC、EIDE、串口速率及32字节/30ms无线节奏不改。未执行烧录、复位或硬件通信。

对比 `Code/reference/2026-09-26/a/Lds50cHost` 的 `RadarCoordinator`/`ApplicationState` 与 `Code/reference/Radar_2026-10-01/Radar`：原主机持续模式每完整圈更新原始点并重算障碍和路线；F407原主机持续模式只提供预览，不发布建图结果，这是已确认的功能缺失。F1主机投影为 `x=230+d*sin(a), y=230+d*cos(a)`，判障网格150～2250 mm、默认阈值1、保护掩码00404405；现有投影/阈值与之相同，不改变来“制造障碍”。

真实日志可完整重放scan3：1496原始点、1331筛选点、1330网格外点，仅R5C5有1点，路线33点。例子角度1.5°、距离2719 mm投影约(301.2,2948.1)，在F1/F407两端都应排除；因此场外或保护格内的物体不能期待红色障碍。单凭数据不能断言供电/方向等具体物理原因。

另有两个已复现的通信问题：稀疏120分区数组被当作前N个有效点发送，导致零距离空格混入、尾部有效点遗漏；无线损坏行出现双 `k` JSON，标准JSON解析保留后一个key，拼接行被误作有效页。没有证据把这些字节缺失统一归因于某个硬件故障。

## 实现

- `radar_host_map` 共享逐点Add/完整圈Finish；原静态Build调用同一实现。持续接收所有原始点，包括超过4096诊断容量的点；完整圈结束才发布计数、掩码与路线。坏帧只丢弃当前不完整圈，保留上一完整结果，不增加恢复门槛。
- `radar_host` 发布持续圈结果及新scan/map/plan；压紧非零预览点，保留最后分区。完整诊断云属于静态圈，不能用旧静态云冒充新持续圈。
- 控制台冻结一份地图/路线，网页确认 `ack plan` 前不替换；最后路径页丢失仍可重复读取。ACK仅释放发送缓存，不能启动/停止雷达或车辆；重复ACK幂等。结果先传，之后一圈预览，再通知最新结果，跳过积压圈。
- 地图与路径整记录按256字节预算合并，分号分隔；offset以记录为单位。典型33路点夹具由原28+33=61页缩至3+9=12页，实际页数随字段/编号长度变化，不写死。预览仍按独立live_id冻结并验证完整CRC。
- 网页持续更新不取消正在读取的同圈结果对；会话/配置变化或显式单圈仍隔离旧请求。损坏JSON、双k拼接不算成功，按原有限页重试。停止锁定允许缓存ACK，但扫描/配置仍沿用原锁定规则。
- 未读回统计显示“—”；图到而路径未到显示“待同步”，真正无路仍显示设备不可达。大量网格外点单独提示位置/0°方向，不改变判障规则，不用预览点替代完整统计。
- 持续模式应用新参数后丢弃不完整圈，下一完整圈生效，不重新启动雷达；无完整原始缓存时不声称同圈重筛选。静态完整缓存的同圈重算不变。旧配置结果不得套新配置身份。
- 配置分页同样冻结值和身份，避免持续圈号更新使27页配置读回无法收齐；正常操作不额外下载配置。
