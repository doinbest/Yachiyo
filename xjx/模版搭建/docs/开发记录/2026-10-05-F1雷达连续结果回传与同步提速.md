# F1 雷达连续结果回传与同步提速 — 2026-10-05

## 问题与定位

用户反馈其他模型提速后，障碍识别正确，但路线不显示，并出现 `ERR radar host page_pending` 与“上一条指令仍在发送，本次未排队”。本轮范围仅为 `#map/radar` 的结果通信，不改实车监控界面、雷达识别或规划算法。

当前网页把地图和路径读取改成 `Promise.all`。共享控制台 `executeSend` 拒绝同时发送两条指令，而固件也只有一个 `Requested` 待分页槽。一个读取失败后，另一个读取仍可能继续，新的状态同步又开始读图，导致重入、`page_pending`、无路径及无 ACK。已经定位并复现，不把正确的障碍识别当作故障原因。

## 本轮实现

- 新增只读命令 `radar host result <plan>`，一次请求由 F407 连续回传同一冻结结果的地图页、路径页和 `host_result_end`。
- 保留原有256字节上限、记录合并分页、五个身份字段及 `fetch` 单页读取。结束标记用 `mp` / `pp` 报告实际页数，不能写死地图28页或每页一个路点。
- 网页不再并发读取地图和路径。当前完整结果确认后再读最新圈，中间圈不排队；同配置的持续状态更新不会打断正在读的结果。
- 结束标记到达时只补读缺页。标记也丢失时，10秒没有有效同圈数据才进入补读；数据推进会延长等待。整组无页先读第0页取得形状，单页最多额外重试两次。
- 同圈地图、路径都完整才 ACK。最后页丢失仍可读冻结缓存；停止取消后续回传，历史完整结果保留。
- 120分区点云预览保留，改为每4次不同结果确认后发送一圈；重复 ACK 不累计。结果请求可抢占自动预览，正常建图不上传完整点云。
- JS / Python 桥接都把 `result` 列为只读，停止锁定下可读，但不能启动扫描或运动。全局发送门槛、停车机制及实车监控未修改。
- 按用户本轮后续明确要求，删除30ms固定等待，保留64字节发送块、USART1 115200、完整报文边界及优先级；不改DL-20配置、IOC或EIDE。此发送层共用变化让其他控制台消息也不再额外等待，但不改变其协议、控制逻辑或界面。

## 30ms是否必要

项目[2026-09-12记录](2026-09-12无线地图遥测限速发送.md)明确说明：当时无线接收出现残缺JSON后加入32字节/30ms限速，但属于待验证试调值，不是模块规格保证。进入本轮时已有版本已改为64字节、30ms未变。用户随后明确要求删除等待，本轮已将 `CONSOLE_TX_GAP_MS` 改为0，并从编译的发送路径中去掉固定等待判断；DMA完成后下一次主循环即可发送后续块。

按115200 / 8N1计算，64字节串口发送约5.56ms，原来随后30ms间隔，连续满块理想吞吐约 `64 / (0.00556 + 0.030) = 1800 B/s`。取消固定等待后，UART字节理论上限为11520 B/s；主循环调度、其他消息和DL-20无线净吞吐仍决定实际耗时，不能把UART速率等同于无线有效速度。

本轮同时减少请求往返、降低预览占用和删除固定等待。发送完成不代表无线送达；缺页可补读，但损坏持续发生会降低实际速度，需保存真实收发日志比较。本轮不承诺固定秒数或已经完成实车速度验收。

## 使用与实物验证

1. 烧录 `Code/template/MDK-ARM/template/template.hex`。
2. 关闭旧本地服务后重新运行 `Code/upper-computer-web/local-car/start.cmd`，使Python桥接的新只读规则生效；网页 `Ctrl+F5` 刷新，固件与网页要一起更新。
3. 人工选择实际COM口，115200连接；点击持续扫描，移动非保护格内障碍。日志应是 `result <plan>`、连续地图/路径页、`ack <plan>`，正常情况下不再逐页请求。
4. 丢页时观察是否只 `fetch` 缺页；不因单次丢页重新扫描或放弃已经读到的地图。比较障碍与路线更新延迟，并保存实际日志检查取消等待后的无线丢页/坏帧情况。

软件验证不代替真实DL-20无线链路、雷达供电与场地验收。
