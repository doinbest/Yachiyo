# 串口张大头步进电机多机控制对照

分析日期：2026-10-16。范围按用户最新要求限定为UART串口总线驱动张大头/Emm协议步进电机。

已确认实际串口调用链的重点参考共6项：GongXun2025、gc-stm32F4-、enginer-train、GX-Intelligent-Logistics-Silver、Gitee塔吊方案的底盘，以及39汐的机械臂。39汐的脉冲底盘不纳入对照；CAN方案、直流电机方案及未确认串口步进调用链的候选不作为本轮结论。

主要结论是：这些工程大多采用“按地址逐台发送”；是否同步生效由运动命令的同步标志和末尾同步触发决定。DMA、RTOS和驱动器自身闭环，均不能单独证明多台电机同步启动、同步到达或任务已经完成。

## 两种串口多机组织

### 逐台发送后立即生效

```text
主控发1号速度 → 1号立即执行
主控发2号速度 → 2号立即执行
主控发3号速度 → 3号立即执行
主控发4号速度 → 4号立即执行
```

总线上仍然可以接多台电机，每台靠地址区分。四条命令存在发送和等待间隔，因此不是同一时刻切换目标。Gitee塔吊方案的四轮速度发送属于这一类。

### 先缓存各轴目标 再统一触发

```text
主控发1号目标，同步标志=1 → 1号先缓存
主控发2号目标，同步标志=1 → 2号先缓存
主控发3号目标，同步标志=1 → 3号先缓存
主控发4号目标，同步标志=1 → 4号先缓存
主控发地址0同步触发 → 等待同步的电机开始执行
```

这利用的是驱动器的多机同步功能。串口没有同时发送四条命令；它先顺序准备，再让驱动器统一执行。GongXun、gc-stm32F4-、enginer-train的所查四轮速度路径使用这一思路；Silver的所查位置动作与39汐机械臂也使用同步准备/触发。

同步触发解决启动时刻问题，不能自动解决路程比例、各轴结束时间和反馈确认问题。例如两个轴分别走100 mm和200 mm，都以相同速度执行，即使同时启动，短行程轴仍会先到；需要共同运动时间或各轴速度规划才能进一步协调。

### GongXun 分时轮发加同步

`StepMotor_Target[5]`保存目标及修改标志。`StepMotor_Callack`按6个槽循环：轮1、轮2、轮3、轮4、同步、5号位置。硬件注释标称TIM6槽间隔1.5 ms；初始化为115200、仅USART发送，发送封装使用DMA并等待前次发送完成。

优点是业务计算不必在每个动作里直接连发四轮。需要注意，四个槽读取的是可被上层更新的各轮目标；所查实现没有在一轮发送前冻结整组快照。因此“最后有同步触发”不等于“四轮一定属于同一次控制计算”。该项目不读ACK，不能据此证明本车也可以取消应答检查。

来源：[StepMotor.c](https://github.com/zpclyn/GongXun2025/blob/19cb6a69ba3580465f58ab9f204dbaf33878c969/控制代码/Hardware/StepMotor.c#L346)。

### gc-stm32F4- 统一计算后顺序发送

`Chassis_Core`更新运动阶段和四轮`motor_v`，再按地址映射循环发送，最后执行`ZDT_DJ_TongBu_Control`。速度封装将同步字节写成1。`Serial_SendHex_DMA`在新发送前等待旧DMA完成，其作用是避免覆盖正在搬运的数据，不是等待驱动受理。

该结构适合研究“先算好四轮、再发这一组”。轮间1 ms是对方115200发送配置下的代码选择，不包含本车八电机反馈、异步通知、停车与恢复的全部预算。

来源：[MC.c](https://github.com/Wuyanzu-wuhu/gc-stm32F4-/blob/a3476a5a309e8676bf9935f51710491cf8c8b057/Hardware/MC.c#L309)。

### enginer-train 反馈路程与速度同步结合

它比纯延时运动多了一层“读四轮位置，再决定后续速度”：先读取各轮当前位置，求已走路程与剩余路程，然后选择加速、匀速或减速目标，经四轮F6缓存和同步触发执行。

值得参考的是反馈参与运动进度，而不是其阻塞while、逐轮固定延时或未经核实的航向调用。四轮位置依次读取也有时间差，不能把它们天然当作同一时刻测量。

来源：[move.c](https://github.com/Ycn115/enginer-train/blob/8f2f08e42ac95fafdfdb0e51af525893c98ff47b/Drivers/Hardware/move.c#L115)。旧[lzw1996145地址](https://github.com/lzw1996145/enginer-train)现重定向到Ycn115，不重复计数。

### Silver 位置同步与估时等待

`Motor_pos`将距离换成脉冲，依方向选取两台电机，用位置模式下发并同步。后面调用`Motor_Delay`等待，按选项执行角度修正。因其运动学和参与轮组合不同，不能把两电机控制直接套成本车四轮公式。

这一例说明：同步FD是一种多机执行机制；后面的完成判定仍可能主要依赖估算时长。具备外部定位接口，也不能自动证明某条位置动作已用新鲜电机反馈闭环验收。

来源：[Motor.c](https://github.com/liaojingwu20041031/GX-Intelligent-Logistics-Silver/blob/c6359fbadc494e281ec3154aabb898b69419deeb/Core/wc/Motor.c)。

### Gitee塔吊方案 底盘UART与机构控制分开判断

电控V2.7.4的`USER_Code/chassis_control.c:SetMotorVoltageAndDirection`构造地址1～4的F6帧，字节6固定为0；函数按顺序阻塞发送，没有追加FF同步。`RTOS_APP/Chassis_task.c`调用该函数，再osDelay(5)。

因此它是四轮串口步进方案，但这条速度路径属于“逐轮立即生效”。FreeRTOS把底盘和塔吊任务分开，不会自动把四条UART命令变为同一时刻执行。该工程的`USER_Code/tower/tower.c`另走CAN，本轮不采用其机构控制作为串口多机证据。

来源：[Gitee工程](https://gitee.com/pinksakura/Logistics_Vehicle_F407_V2)，核对提交`4101ec28f1c7b968192bc09def869e88a4ea1dd7`；本地研究副本保留对应文件。

### 39汐 只取UART机械臂

`robocal.py`的`MoveJ_AccDec`是清晰的三轴准备/触发案例：先算三个关节目标，分别发送位置及速度/驱动加速度参数，再执行一次同步。每条位置命令之间有3 ms休眠。串口发送由`ZDT.py`封装，锁能避免线程同时写数据，但不能证明Linux线程调度具有3 ms硬实时精度。

接收代码处理FD/9F到位通知和位置回复；到位通知使用共享标志，部分动作还估算最长运动时间。按需启用通知与每条命令均关联独立动作/地址的反馈确认，是不同的可靠性层次。它的底盘使用定时器STEP，不用于解释本车UART四轮的吞吐和应答竞争。

来源：[原始工程](https://github.com/Thirtynine3939/2025GongChuang_AGV/tree/f1fbab3605f4941fdc14a13d9380aa48700a4b87/程序)，所查上位机初赛/决赛机械臂文件及`ZDT.py`快照位于本地研究目录；下位机压缩包不作为UART底盘证据。

## 对本车最有用的比较

### 同步启动 同步到达和闭环确认分别处理

| 层次 | 解决的问题 | 单靠它不能证明什么 |
| --- | --- | --- |
| 不同电机地址 | 命令发给哪台电机 | 多轴同时启动 |
| DMA与发送互斥 | 字节可靠送出、缓冲不被并发改写 | 驱动已受理、已到位 |
| 同步标志与触发 | 先缓存后统一执行 | 各轴同时完成、沿期望轨迹运动 |
| 各轴速度及加减速规划 | 按共同时间协调不同路程 | 轮地不打滑、机构没有故障 |
| 匹配动作的反馈与新鲜停稳 | 核验受理、运动进度、最终状态 | 整车真实位置完全无误差 |

对于四轮平移，应先用同一车体速度/航向计算整组轮速，再发送这组数据。对于机械臂不同轴，既要考虑共同运动时间，也要考虑独立机械边界及到位证据；仅把四台或三台的速度填成相同数值并不等于轨迹协调。

### 串口带宽限制仍然存在

按115200、8N1和上述常见8字节F6、4字节同步帧估算：四轮命令加同步共36字节，单纯发送线时约3.125 ms；若每轮还有4字节ACK，再增加约1.389 ms。这里未包含驱动响应、帧间交接、位置/速度查询、机械臂动作或线程调度。

因此1 ms控制计算不代表每1 ms都能完整发送、应答并刷新全部电机。各开源的1 ms、1.5 ms或3 ms代码间隔也不能直接拼成本车的保证周期。

### 广播同步的作用域需要核对

地址0同步触发会作用于符合驱动协议、已经缓存同步运动的电机。底盘和机械臂共享线路时，要防止机械臂尚未准备完成的同步缓存被底盘广播提前触发。同步批次应有明确所有权；非同步位置命令是否立即执行、驱动缓存怎样清理，须按本车驱动版本处理。

### 本车可借鉴的组合

- 以gc-stm32F4-的“统一计算、顺序准备、最后同步”研究四轮发送组织。
- 以GongXun研究业务目标与发送调度分开，但保留本车整组目标快照，不能将其仅TX当作取消ACK的依据。
- 以enginer-train研究反馈路程参与加减速，使用本车已有非阻塞调度和共同测量时间处理，避免照搬长while和延时查询。
- 以39汐UART机械臂研究三轴位置同步及共同运动时间，保留本车动作匹配、新鲜反馈与停稳确认。
- Gitee和Silver用于对照“未同步的速度模式”“同步位置但估时完成”，不能据其代码简单程度认定本车可以省掉反馈或直接改成固定等待。

本车现有四轮同步、底盘Receive、ID5～8固定Both与动态Receive、发送队列及反馈取证的具体行为仍以当前源码和实物为准。本轮只比较公开实现，没有提出更换总线或取消现有反馈的修改。
