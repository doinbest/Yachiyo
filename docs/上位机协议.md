# 当前 USART1 文本控制台协议

以当前 `template/App/arm_console.c`、底盘子模块及 `upper-computer-web/local-car/protocol.mjs` 为准，整理于 2026-09-21。适用 STM32 USART1 无线文本控制台；香橙派 USB CDC 使用 B2 二进制视觉协议，不能发送本页文本命令。

旧 `sys.ping#` / `motor.*#` 协议已退役，仅保存在[历史协议](开发记录/历史Zigbee网页原型协议.md)。B3 命令继续返回 `ERR Unsupported B3`，已移除对应 C API。

## 帧、单位与结果

- USART1：PA9/PA10，当前 115200 / 8N1。端口由现场确认。
- 网页发送单行 ASCII，追加 CRLF；固件接受 CR 或 LF 行结束。命令内容最多 63 字节、6 个空白分隔字段，网页禁止内嵌换行。
- `OK` / `accepted` 表示命令的具体受理或查询结果，不统一代表到位；`ERR` 表示拒绝或错误。命令回显和异步日志可能交错。
- `pos` 是电机轴相对角度；网页限 ±360°，不能将网页限值当作固件所有轴的机械限位。
- `chassis run/heading` 使用车体前向 vx、左向 vy（mm/s）、逆时针 omega（rad/s）；旧 `chassis velocity` 的 yaw 单位为 °/s。
- `chassis move/origin` 使用地图 +X 向右、+Y 向上，地图角度与 HWT101 模块角度分开。
- 网页 `seconds` 转为整数 `hold_ms`；起步和停车各 500 ms。四轮顺序 FL/RL/RR/FR=1/2/3/4。

## 补充接口与操作语义

- `chassis stream on <非零uint32会话编号>` / `chassis stream off`：手动遥测订阅。
- `chassis stop [非零uint32客户端编号]`、`chassis stop-status`：独立停车与查询，详细语义见下文。
- `screen status`：读取 USART3 屏幕通信统计，可通过手动终端发送；不属于网页快捷按钮。
- `imu verify 10` 是 `imu verify` 的兼容别名。`imu verify 120` 已移除，返回格式错误。
- `imu cal clear` 为兼容入口，取消当前标定/验证并清除本次验证资格；`imu cal forget` 返回 `ERR imu cal forget deprecated no_erase=1`，不擦除存储。它们不恢复旧软件补偿方案。
- `chassis run vx vy 0 hold_ms` 保持起步模块航向，须本次 IMU 验证通过且数据新鲜，不要求地图原点；非零 omega 执行给定转向。`chassis heading` 仍需锚点。
- `imu cal start` 为约 20 秒原生标定及 30 秒自动验证；独立 verify 为归零后的 10 秒静止验证。重新验证会撤销旧航向资格，需重新建立地图原点。
- `imu status` 的 `zero_requested/zero_sample_received/zero_before_deg/zero_after_deg` 区分归零请求与后续样本；HAL 成功不单独证明实物归零完成。
- `stop all` 的作用取决于当前任务，不能等同整车硬件急停。`material auto` 的 ALIGNED 仅表示对准完成。
- 本车驱动应答模式、65536 位置单位/圈及轮向必须核实；不能以 3200 命令脉冲/圈替代反馈单位。`chassis reset-confirmed` 不操作硬件复位。

## 二维码查询与事件

查询不消费主循环任务码，跟随开关不启动扫码器。

| 命令 | 含义 |
|---|---|
| `qr status` | 读取接收统计，不消费任务码 |
| `qr read` | 读取最新有效缓存，可重复读取 |
| `qr stream on/off` | 开启/关闭新码事件上报，不控制扫码器 |

回复形式：

```text
OK qr status valid=0 seq=0 age_ms=NA received=0 accepted=0 rejected=0 uart_errors=0 stream=off event_dropped=0
OK qr read valid=0 seq=0 code=NA age_ms=NA
OK qr stream=on
EVT qr code seq=1 code=123+231+312+123 age_ms=0
```

有效原码为四组三位数字；`seq` 与 MCU 毫秒时间为 uint32，可回绕。`age_ms` 是 MCU 计算的最新有效码年龄，没有有效码时为 NA。`received` 按字节、`accepted/rejected` 按完整帧、`uart_errors` 按 UART 错误计数。重复有效码同样递增序号；没有新码不表示离线。新码事件最多 5 Hz，只保留最新待发事件，`event_dropped` 与地图丢弃统计独立。格式化与发送在主循环运行；主循环原单次消费接口保留。

详见 [八千代控制台与二维码接入](开发记录/2026-09-12八千代控制台与二维码接入.md)。


## 实车反馈距离与前四段路线

新增`chassis move <map_dx_mm> <map_dy_mm>`（相对地图位移、长度>0且≤300 mm）、`chassis route start|next|status|cancel`。原点仍需显式`chassis origin`设置。路线前四段固定，每段反馈确认停车后等待人工next，不由网页动画驱动。`chassis stop`取消路线资格；`chassis task`为距离任务增加目标、误差、反馈有效性和停车确认查询行。

`@CHASSIS`版本仍为1，新增可选状态：

- `localization`：generation、feedback_tick、origin_valid。
- `route`：state（idle/running/stopping/waiting/done/error/cancelled）、reason、segment（0或1～4）、action_id、target（地图X/Y mm、航向deg）、error（地图dx/dy mm、航向误差deg）、feedback_valid、stop_confirmed。
- `distance`：仅距离任务输出；active、state（运动任务状态）、reason、action_id、target/error数组及feedback_valid、stop_confirmed。独立move清除旧路线显示；活动路线段显示优先。

`feedback_arrived`和stop_confirmed表示轮子反馈估计到站并满足停止条件，不表示视觉精确对准。等待人工继续期间仍占用任务；查询/停止允许，其他运动/标定/修改定位配置拒绝。详见[实车前四段反馈路线](开发记录/2026-09-12实车前四段反馈路线.md)。

## 机械臂通信错误

现有 `enable/disable/state` 命令不变。单轴错误增加总线隔离状态：

- `ERR motor tx bus_locked=0/1`：请求未能提交到电机发送层。
- `ERR motor communication axis=base bus_locked=0/1`：异步传输失败，没有有效电机返回码。
- `ERR ack_timeout axis=base state_unknown bus_locked=0/1`：未在期限内收到合法应答，不能据此判断电机没有执行命令。

`bus_locked=1` 表示共享 UART5 总线处于故障隔离，后续普通电机请求会被拒绝；不是网页按钮失效，也不是驱动实际复位的证明。参见[UART5 循环 DMA 修复记录](开发记录/2026-09-12UART5循环DMA与单次失能故障修复.md)。

## 地图遥测与发送节奏

协议仍为 `@CHASSIS` v1，原有状态字段保留。config 新增可选整数 `telemetry_period_ms`，当前值为 `2000`。网页未收到该字段时按旧固件 200 ms 周期处理；首次配置等待 8 秒，配置后接收超时为周期的三倍。MCU 反馈安全时限及网页依据 MCU 时间检查的样本有效性均未放宽。

USART1 采用最多 32 字节一段、完成后间隔 30 ms 的非阻塞发送。已开始的逻辑帧保持完整，帧结束后的选择优先级为回复、二维码事件、地图遥测。回复队列以最多 256 字节选取，仍按 32 字节分段发送。积压时不生成新地图快照；stream off 取消待发快照，完成正在发送的帧。`dropped` 仅是软件队列统计，不能代表无线链路丢字数量。

这些发送参数是待上板确认的调试值。实际改变的是输出节奏，不改变控制周期、串口波特率、位置控制或运动指令。参见[无线地图遥测限速发送](开发记录/2026-09-12无线地图遥测限速发送.md)。


遥测按会话接收：先 config 后 state，版本为 v1；几何来自 config，不能用离线默认值替代。重复/乱序 MCU 时间丢弃，配置或 trace_seq 变化断开轨迹。指令推算与反馈估计分开，反馈有效性要求四轮位置、采样时间及航向有效；网页按 MCU 时间检查 600 ms 新鲜度。


## 本地服务与独立停车查询

当前网页共享模式默认 COM23 / 115200 / 8N1，由本机服务独占；该默认值不替代现场端口确认，网页和 CMD 共享接收事件。服务只监听 `127.0.0.1:8765`。GET `/api/status` 获取启动会话 token；POST 须携带同源 Origin 及 `X-Console-Token`，脚本同样遵守这两个请求头。

| 接口 | 用途 |
| --- | --- |
| GET `/api/status` | 连接、停车、配置、准备锁定与最新事件编号 |
| GET `/api/events?after=N` | 读取编号之后的事件；gap 表示记录窗口已过期 |
| POST `/api/connect` | 显式 `port`、`baudrate`，网页当前传入 COM23、默认115200 |
| POST `/api/send` | 单条 ASCII `command`；返回排队编号，不等于发送完成 |
| POST `/api/stop` | 清空待发命令、取消准备、锁定运动并优先停车 |
| POST `/api/resume` | 明确解除软件停止锁定，不启动任务 |
| POST `/api/disconnect` | 先请求停车、最多等待 6 秒，再释放串口 |
| POST `/api/config` | 保存人工确认的 profile、units_per_rev、directions_confirmed |
| POST `/api/preparation` | active、owner；限定准备所有者的配置命令，其他来源只允许查询/取消/停止；150 秒超时释放 |

事件包括实际 TX、原始 RX 行、连接变化、停止和系统信息。浏览器使用 TX 事件确认已经写入串口；设备处理和物理执行仍以各自回复判断。原始字节和分块时间保存在 `.embeddedskills/logs/serial/`。

2026-09-14 修正：事件对象 `id` 始终为递增流游标；停止事件的 MCU 停车编号使用 `stop_id`，不可覆盖事件 `id`。GET status 返回的 `stop.id` 保持为 MCU 停车编号。

固件新增原始 `0x03`（Ctrl+C）处理，清除未完成输入、取消底盘路线及可继续驱动底盘的自动任务。`chassis stop [非零uint32客户端编号]` 与 `wheel stop` 共用同一停车入口。客户端重发同编号不会重建请求；新的运动会使旧停止确认失效。普通手动停车可省略编号。

`chassis stop-status` 和停车受理返回：

```text
OK chassis stop id=1 token=123 requested_ms=100 tx_complete=0 wheels_stopped=0 reason=pending_tx
```

`tx_complete` 是电机总线停车发送完成；`wheels_stopped` 是发送后至少三组新鲜四轮反馈覆盖 500 ms、各轮速度绝对值 ≤1 RPM、相邻位置变化 ≤2 mm 的独立停止确认。无需到达地图目标或有效 IMU，但必须有有效反馈和已确认的位置单位。常见 reason 为 pending_tx、monitoring、stopped、missing_feedback、timeout、new_motion、tx_failed。

软件请求发出、MCU 受理、发送完成和反馈停止分开显示。旧固件的通用 OK 不能完成本次停车确认；无线失联不能保证停车。详见 [共用控制台与停车记录](开发记录/2026-09-12COM23共用控制台与软件停车.md)。

### 同步取消后的只读诊断（2026-09-14）

运动中停车可能保留 sync_cache_uncertain / locked=1；这表示运动禁止，不应解释为所有状态查询失败。取消底盘运动应答造成隔离时，已开启的四轮反馈可在停车发送结束后继续读取。真实UART故障/超时仍阻止轮询。chassis stop-status 的 wheels_stopped 与运动解锁独立，确认停止不会自动恢复运动。

恢复仍要求实际驱动器复位后再使用 chassis reset-confirmed（主控未重启时），不自动发送该命令。执行前先停止反馈轮询并等待在途事务完成；主控也重启时按正常准备流程重新建立资格。
