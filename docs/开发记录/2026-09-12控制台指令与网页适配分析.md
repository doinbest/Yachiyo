# 控制台指令与网页适配分析

日期：2026-09-12。对象：当前 `模版搭建` 工程与 `upper-computer-web/local-car/`。

本轮为源码分析，只新增分析文档与索引，没有修改固件或网页，也没有发送硬件命令。下文区分当前实现、源码推断和修改建议；建议接口不代表已实现。

## 1. 结论

现有“中文按钮 → ASCII 命令 → STM32 执行”的方向适合本地小车，不需要为了减少手工输入改成十六进制协议。主要问题是网页目录落后于固件、停止命令作用范围不统一，以及反馈尚不足以驱动二维地图。

优先顺序建议：

1. 修正停止语义与失败反馈，确保停止后任务和周期发送都结束。
2. 网页移除已经失效的 B3 圆环入口，补上 IMU、航向测试和链路查询。
3. 按“日常操作 / 标定设置 / 诊断测试”减少首屏需要理解的命令；保留有用的底层诊断。
4. 核准位置单位与底盘参数，再补二维地图需要的运动状态和定位反馈。

此前的 [指令精简计划](../superpowers/plans/2026-09-11-console-command-cleanup.md) 仍是计划，不能当作已完成的实现。其网页位置单位、停止行为和 IMU 命令表需要按本次核查更新后再执行。

## 2. 当前链路和协议边界

```text
本地网页的中文操作
  → protocol.mjs 生成单行 ASCII
  → serial.mjs 写入 PC 所选串口
  → Zigbee / USART1（115200，8N1）
  → ArmConsole_Process / ArmConsole_CommandExecute
  → 机械臂、底盘、IMU、视觉模块
  → UART5 电机 / I2C2 HWT101 / 原生 USB CDC 香橙派
```

- 当前控制台是大小写敏感的空格分隔文本，以回车/换行结束；网页统一发送 CRLF，正文最多 63 字节、6 个字段。
- `docs/上位机协议.md` 中的 `sys.ping#`、`motor.speed=...#` 是已标注的历史协议，不能用来配置当前网页。
- PC 控制台与香橙派视觉链路是两条链路。当前视觉是 USB CDC 上的 B2 六色协议，不能把香橙派的识别帧直接作为 PC 控制命令。
- 编号 `1/2/3/4/5/6` 对应红/黄/蓝/绿/黑/浅蓝，建议网页直接显示颜色名称；当前网页只显示“编号”。
- `pos x ...` 的 `x` 是机械臂伸缩轴；`chassis velocity` 的前向/左向速度是车体坐标，均不等于二维地图的世界 X/Y。

依据：[命令解析](../../template/App/arm_console.c)、[网页命令表](../../upper-computer-web/local-car/protocol.mjs)、[串口层](../../upper-computer-web/local-car/serial.mjs)、[颜色定义](../../template/Hardware/Camera.h)。

## 3. 需要先解决的实际问题

### 3.1 停止命令还没有一致、完整的作用范围

| 入口 | 当前源码行为 | 影响 |
| --- | --- | --- |
| `stop all`，没有视觉任务运行 | 调用 `MechanicalArm_Stop(ALL)`，最终向地址 0 广播停止；没有清除普通底盘速度刷新状态 | 不能保证底盘保持停止，也不是严格的“仅停止机械臂” |
| `stop all`，视觉任务运行 | 调用两套视觉停止函数；实际停止哪些运动取决于各自 busy 状态 | 同一命令的清理范围取决于当前任务 |
| `chassis stop` / `wheel stop` | 同一分支；机械臂忙时拒绝，否则调用 `Mecanum_Test_Stop()`，清除刷新并发送四轮停止 | 两个名字不是两种功能；忙时回复建议使用 `stop all`，但后者又有上述缺口 |
| `chassis velocity 0 0 0` | 调用停车但忽略返回值，无条件输出 `OK chassis stop` | 发送失败也可能得到成功提示 |
| `vision stop` | 调用 `ArmVision_Stop()` 与 `MaterialVision_Stop()` | 停的是两套视觉任务；不是仅机械臂视觉，也不等于所有手动运动 |
| `material stop` | 只清理物料协同任务；忙时停车并停止机械臂 | 与 `vision stop` 存在包含关系，可留在诊断区 |
| `camera stop` | 视觉任务忙时拒绝，否则结束识别请求/查看 | 不应标成“整车停止”或“关闭香橙派程序” |

**源码确认的恢复发送路径：** `chassis velocity ...` 设置 `MecanumVelocityActive=true`；无视觉任务时执行 `stop all` 只走机械臂广播停止路径；主循环仍调用 `Mecanum_Velocity_Process()`，它每 100 ms 再发送之前的速度目标。广播停止若已成功，后续速度命令仍可能使底盘继续运动。这个结论来自调用链，尚未通过实车重现。

相关位置：`arm_console.c` 1271、1347、1510 行；`mechanical_arm.c` 的 `MechanicalArm_StopAllSend()` 和 `MechanicalArm_Stop()`；`mecanum_chassis.c` 的 `Mecanum_Velocity_Process()`、`Mecanum_VelocityRefresh_Stop()`；`main.c` 589 行。

建议先定义清楚三个动作：停止当前视觉任务、停止底盘、停止全部电机运动。全部停止应先取消上层任务及周期目标，再发停车命令，并据实际发送结果反馈。共享 UART5 上地址 0 的广播会涉及底盘 ID 1–4 和机械臂 ID 5–7；不能只改网页文字而保留底层作用范围不一致的问题。这里的“全部电机”也不应被描述为已断电或硬件急停。

### 3.2 网页仍提供固件明确拒绝的命令

`protocol.mjs` 33、36 行仍生成 `vision calib <1..3>` 和 `vision ring <1..3>`。当前 `arm_console.c` 1784–1791 行明确返回 `ERR Unsupported B3`。

建议删除这两个网页入口，保留固件对旧协议的明确拒绝。仅删除目录仍不够：旧收藏保存的是完整命令字符串，`app.mjs` 载入时只检查帧格式，因此旧圆环命令仍能通过收藏发送，需要一起迁移或移除。

反过来，固件已有的 `imu ...`、`chassis hold/status`、`camera status`、`screen status` 尚未出现在网页命令表。

### 3.3 “位置脉冲”标签与实际回包单位不一致

`MechanicalArm_ResponseProcess()` 直接把 `0x36` 回包符号和四字节数值解码到 `CurrentPosition`；`ArmConsole_MotorEventHandle()` 随后输出 `pulses=...`，网页也标为“脉冲数”。

但本地 [X42S 手册](../硬件资料/执行机构/闭环步进电机/ZDT_X42S第二代闭环步进电机用户手册V1.0.5_260527.pdf) 第 72 页、5.5.13 节规定：Emm 实时位置按 `angle_deg = signed_raw × 360 / 65536` 换算。它不同于位置命令按细分设置得到的命令脉冲数。

以 3200 命令脉冲/圈的假设为例：一圈运动命令是 3200 脉冲，而一圈实时位置约为 65536 协议单位，两者不能直接相减或套同一个转换函数。建议保留原始值用于诊断，同时输出明确单位的角度；实际驱动型号和协议版本仍需匹配实物。

### 3.4 视觉命令名称相近，但不能合并成同一动作

| 命令 | 当前职责 | 网页推荐名称 |
| --- | --- | --- |
| `camera material <color>` | 请求识别和查看；不驱动对准机构 | 仅识别颜色 |
| `vision material <color>` | 使用 Base/X 机械臂进行视觉对准 | 机械臂对准 |
| `material auto <color>` | 包含 Base 回零，使用底盘前后与 X 轴修正进行对准 | 底盘协同对准 |
| `vision calib material <color>` | 机械臂视觉响应标定 | Base/X 视觉标定 |
| `vision calib chassis <color>` | 测量底盘/X 的像素响应 | 底盘/X 响应测量 |

当前 `material auto` 并没有组成 Z 轴下降、夹爪抓取、抬升、运输、放置的完整流程，不能显示为“一键搬运完成”。

`MaterialVision_CorrectionStart()` 使用固定 PID 参数，没有读取 `MaterialVision_Calibration` 响应矩阵；因此不能把 `vision calib chassis` 宣称为当前 PID 对准必需的前置标定。可以保留它作为测量工具，后续若采用响应矩阵控制再接入。

依据：[ArmVision.c](../../template/App/ArmVision.c)、[MaterialVision.c](../../template/App/MaterialVision.c)。

### 3.5 夹爪三个命令当前给出相同输出

[Arm.c](../../template/App/Arm.c) 中 `Idle/Open/Catch` 三个常量目前都是 7.50%。因此按钮名字不同不代表实际开合不同。`open/catch` 功能有必要保留，先通过实物确定各自参数；`idle` 的独立需求确认前可从日常界面隐藏，不应凭名称猜测舵机角度。

## 4. 命令保留与精简表

表中是建议，当前固件入口保持原样。`axis` 为 base/z/x；只有注明 all 的接口允许 all；`color` 为 1–6。

| 当前指令 | 处置建议 | 关键说明 |
| --- | --- | --- |
| `help` / `info` | 保留；帮助放诊断，信息放连接区 | 当前 info 是文本设备信息，尚无完整能力协商 |
| `enable <axis/all>` / `disable <axis/all>` | 保留，机械臂区 | 不是底盘四轮使能接口 |
| `pos <axis> <degree>` | 保留，机械臂微调 | 相对电机轴角度；并非关节末端 mm 或绝对坐标 |
| `state <axis/all>` | 保留 | 电机状态查询；与单纯“收到 OK”不同 |
| `position <axis>` | 保留并修正单位 | 当前返回原始位置值；不支持 all |
| `stop <axis/all>` | 保留接口需求，优先修正 all 的范围 | 当前 all 会广播到整条电机总线 |
| `config <axis/all> [rpm acc limit]` | 保留，标定区 | 当前 RAM 的后续 pos 参数，复位恢复默认；不是修改驱动器所有配置 |
| `home <axis/all> <mode>` | 保留，标定区 | 会运动；模式 near/dir/collision/limit 必须匹配机构 |
| `origin <axis/all>` | 保留，标定区 | 保存机械零点；与回零运动不同 |
| `zero <axis/all>` | 保留，标定区 | 当前位置计数清零；不能代替原点定位 |
| `grip open` / `grip catch` | 保留，日常区 | 当前占空比相同，待实物标定 |
| `grip idle` | 日常隐藏，底层可保留 | 不必为了少一个按钮删除能力 |
| `grip duty <2.5..12.5>` | 保留，标定区 | 校准 PWM 占空比，不用于普通操作者反复输入 |
| `chassis forward/backward <1..200>` | 保留作短距离测试 | 单位 mm，整数；不是完整路径导航 |
| `chassis backward` | 隐藏并考虑弃用 | 无参数时变成持续 30 mm/s 后退；可由 velocity 表达 |
| `chassis velocity <forward> <left> <yaw>` | 保留，手动控制/诊断 | 前、左为整数 mm/s，yaw 为整数 °/s；范围分别 ±1000、±1000、±360 |
| `chassis stop` | 保留并修正忙时停车路径 | 作为底盘统一停止入口 |
| `wheel <fl/rl/rr/fr> <rpm>` | 保留，诊断区 | ID 对应 1/2/3/4；±100 RPM，拒绝 0 |
| `wheel stop` | 网页合并到 chassis stop | 固件别名可先兼容，确认无调用者后再删 |
| `chassis hold <speed> <seconds>` | 补网页，诊断区 | ±100 mm/s、1–10 s；独立航向保持测试，不是通用地图任务 |
| `chassis status` | 补网页并准确标注 | 目前仅返回航向测试状态，不是完整底盘状态 |
| `camera material <color>` / `camera stop` / `camera status` | 保留，识别诊断区 | status 尚缺网页入口 |
| `vision ref` | 保留，标定区 | 建立视觉参考，并使原机械臂视觉标定失效；不会自动回零 |
| `vision calib material <color>` | 保留，标定区 | 过程中机构会运动 |
| `vision calib chassis <color>` | 保留，诊断区 | 当前 PID 不使用其响应矩阵 |
| `vision material <color>` / `vision status` | 保留，日常对准区 | 对准与完成抓取要分开 |
| `material auto <color>` / `material status` | 保留，日常对准区 | 当前为另一套执行机构组合 |
| `vision stop` | 保留常用入口 | 停止两套视觉流程；应显示真实范围 |
| `material stop` | 可藏入诊断区 | 只取消底盘协同任务 |
| `vision ring ...` / `vision calib <1..3>` | 删除网页目录及旧收藏 | 当前固件已拒绝 B3；不是删掉现用 B2 功能 |
| `imu status` | 补网页，状态区 | 角度、新鲜度、校准/验证及 I2C 状态 |
| `imu cal start` | 补网页，标定区 | 当前是模块原生零偏标定约 20 s + 静止验证 30 s，不再是旧版 60+120 s 软件拟合 |
| `imu verify` / `imu verify 120` | 补网页，验证区 | 默认 30 s 或显式 120 s；用于验证已经标定的模块 |
| `imu cal cancel` / `imu cal clear` | 网页只提供 cancel 对应动作 | 两者当前同一分支，取消并清除本次开机验证，保留模块零偏；不是恢复出厂 |
| `imu cal forget` | 不提供正常入口 | 已返回 deprecated/no_erase；不可标成擦除 Flash 标定值 |
| `imu stream on/off` | 补网页，用单个开关 | 校准忙时禁止开启，校准开始自动关；关日志不停止采样 |
| `screen status` | 补网页，诊断区 | 串口屏通信统计 |

网页不需要把这张完整表一次全部铺开。建议首屏按连接信息、底盘操作、夹爪、两种视觉对准和任务状态组织；回零/零点/标定折叠到设置，单轮/原始命令/响应测量放诊断。

## 5. 开源代码怎么借鉴

本次实际读取前轮已下载的本地源码快照；尝试在线打开 GitHub 固定提交页面未成功，因此没有据此宣称项目最新状态。下面链接固定审阅提交，结论限定在对应文件。

### 5.1 gongchuangsai_MBH：按动作分类的文本指令

[源码快照](https://github.com/cheese-shredded-ice/gongchuangsai_MBH/tree/debe55def09374ad147e131f2ee0095412dfcdcd)，`电控程序/BMH-决赛/USER/cmd_parser.c`。

定义了 `SERVO`、`LIFT`、`PID`、`CAR`、`CAR_DIST`、`MOVE_ARM`、`GRIPPER` 等动作。值得借鉴的是让操作者选择“底盘距离、升降、夹爪”这类功能，而不是每次填电机原始帧。你当前的 `chassis`、`grip`、`vision` 已经具有这个基础。

不能照搬的部分：`STOP`（313–316 行）只回复 `OK:STOP`；`WAIT_RPI`、`RPI_CALIB` 在命令处理函数内循环等待；`CAR` 非法类型分支打印错误后仍会落到 `OK:CAR`；大量 `atoi/atof` 缺少严格的非法输入检查。且本次在该决赛源码目录检索，未找到 `CMD_Process/CMD_FeedChar/CMD_Init` 定义之外的调用，不能凭这个文件认定它已经接入实际主循环。

### 5.2 enginer-train：界面动作码驱动业务标志

[源码快照](https://github.com/Ycn115/enginer-train/tree/8f2f08e42ac95fafdfdb0e51af525893c98ff47b)，`Drivers/Hardware/serial_task.c` 与 `control.c`。

串口屏按键码映射到业务标志，例如 `0x01 → start_flag`、`0xC1 → turn_self_zero_flag`；控制函数再调用 `competition()` 或 `HW101_adjust()`。可借鉴“页面选择功能 → 固件执行一项明确任务”的组织方式。对你当前 PC 网页，没有必要把可读的 `imu cal start` 换成必须查表的 `0xC1`。

### 5.3 2025GongChuang_AGV：控制模式与标定入口分开

[源码快照](https://github.com/Thirtynine3939/2025GongChuang_AGV/tree/f1fbab3605f4941fdc14a13d9380aa48700a4b87)，压缩包解出的 `Chassis_v2.0/Drive/Source/button_scan.c`，92 行起。

`Bluetooth_Data_Receive_Task()` 从数据包解析 `Yaw_SetZero`、`ZerobiasCali`、`PID_En`、`World_En`、位置目标和速度参数。它把“航向参考归零”和“零偏校准”做成不同入口，也显式区分坐标/控制模式，这对你的二维地图界面有参考价值。

其位域协议和 `Speed_X_x10`、`Kp_x1000` 等缩放约定不能直接套到当前文本协议。现阶段可以借鉴界面含义，保持已有 mm/s 和 °/s；地图坐标模式、绝对位置动作要等固件实现后再开放。

共同结论：开源命令名字短不等于使用方便；把单位、状态和动作边界讲清楚，比改为二进制或简单删命令更有价值。

## 6. 当前反馈还不足以支持二维地图执行任务

网页 `serial.mjs` 的锁只持续到 `writer.write()` 完成，没有等待 MCU 接受或动作结束。这个行为适合手动串口工具，但不能据此自动连续执行地图路点。

当前 `describeReply()` 已经把 `accepted` 与 `reached=1` 区分，这是应该保留的行为。不过普通 `OK` 只是收到回复；网页没有请求序号，也没有把日志关联到特定一次动作。视觉过程、IMU 连续输出和命令回显会混在同一接收流中。

建议分阶段补充以下能力，仍可使用简单 ASCII：

| 地图需要的能力 | 当前情况 | 后续最小建议 |
| --- | --- | --- |
| 坐标和单位一致 | velocity 接受车体前/左 mm/s 和 °/s | 先固定车体与世界坐标转换；地图若使用 rad/s，发送前明确转换。不要静默把小数交给整数解析 |
| 判断底盘是否执行中 | `chassis status` 只看航向测试 | 扩充为当前模式、busy、目标速度、任务编号、结束原因；目标值与实测值分开 |
| 知道命令是否被接受、是否完成 | 各功能 OK 含义不同 | 区分 accepted/running/done/error；先串行执行一项任务，再按需要增加请求编号 |
| 获取实际 x/y/yaw | 没有完整位姿上报接口 | 先显示仿真预测位姿；轮反馈/视觉定位接入后再显示测量或估计位姿，并标明来源和新鲜度 |
| 控制任务取消 | 停止路径存在上述缺口 | 先完成停止与状态清理，再开放地图连续执行 |
| 关闭页面或失联时处理速度命令 | 断开串口不发送停车，MCU 持续刷新速度 | 为未来遥控入口设计 MCU 端超时停车或有时限速度命令；正常断开时发送停车不能覆盖掉线情况 |

不要在当前网页上先放一个“去往 X/Y”的可执行按钮，再把它暗中换成多条 `chassis forward`。那样既缺侧向/旋转位置任务，也缺真正的动作完成反馈。

另外，[底盘参数配置](../../template/App/chassis_config.h) 当前仍是轮径 100 mm、轴距 150 mm、轮距 250 mm；用户最新提供的是约 210 mm、240 mm，轮径暂定 80 mm。必须按 [二维地图设计基线](../开发规范/底盘参数与二维地图控制设计基线.md) 核准参数后再用来推算地图运动。几何尺寸、方向和反馈单位有误，不能靠修改上位机命令名称解决。
