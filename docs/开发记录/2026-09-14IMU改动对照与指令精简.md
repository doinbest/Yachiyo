# IMU 改动对照与指令精简

## 对照依据与限制

已对照 `.embeddedskills/backups/prepare-route/template/App/hwt101_calibration.c` 与当前源码，结合 2026-09-12 原生标定开发记录及用户本日串口日志。此模块仍是未跟踪文件，没有完整的逐次 Git 历史；备份能证明标定状态机差异，不能证明每次实物烧录的二进制完全一致。

## 哪些改动可能相关

| 改动 | 与本次故障的关系 |
| --- | --- |
| 早期 STM32 拟合并扣除漂移 → HWT101 WORKMODE=1 原生获取零偏 | 改变了模块实际工作模式。早期软件补偿 PASS 不能证明原生标定路径可靠。 |
| 默认独立验证从 30 秒改为 10 秒 | 改变验证时长，不改变原生标定的 20 秒等待；没有在第 10 秒退出原生标定的分支。 |
| 验证前新增 0x76 归零 | 原生标定中，要等 20 秒、正常模式回读成功后才执行。两次错误发生在约 10 秒且 zero_requested=0，因此不是本次运行的归零写操作直接引起。此前运行归零是否有模块侧影响，日志不足以排除。 |
| 标定期间持续读取角度 | 旧备份中已存在。关闭 stream 只关闭输出，不停止 I²C 采集。可能与模块标定期间的行为有关，但尚未证实。 |
| 新增 zero 前后状态字段 | 只记录和显示，未改变 I²C 驱动超时或引脚。 |

用户两次失败分别为 10387、10395 ms；imu_read 最大 6 ms，恢复阶段最终 HAL_BUSY，尚未进入验证。当前日志没有保存最初 HAL 错误码/总线状态，不能从最终 HAL_BUSY 反推第一个失败原因，也不能断言是上拉、接线或模块损坏。

## 已确认的软件诊断缺陷（本轮未作为通信修复实施）

1. StartRun 在条件检查前清空 cal；离线重试会覆盖上一轮失败、寄存器缓存及测量值。
2. 恢复模式失败覆盖最初的 reason/HAL；失去第一现场。
3. 任何 FAILED 都触发耗时报告，包括尚未开始采集的启动拒绝。
4. 驱动离线仅重新探测，不做总线恢复，也未统计探测失败次数。因此错误计数不增长不能证明总线已恢复。

接下来的诊断应先保留首次错误（操作、寄存器、HAL 状态/错误码、I²C 状态、BUSY 与 SDA/SCL），再做标定等待期暂停角度采集的独立对照实验。暂停时必须同时调整该阶段的新鲜度检查，否则会被自身 300 ms 过期条件中止；恢复后必须等待新样本。不要一次加入暂停采集、长超时和总线复位，否则不能解释哪个改动起作用。现有证据不支持把任何候选方案称为已修复。

## 本轮已完成：精简操作入口

| 保留的主要命令 | 含义 |
| --- | --- |
| imu status | 查看通信、模式、零偏与最近结果 |
| imu verify | 归零后完整验证 10 秒 |
| imu cal start | 原生获取零偏 20 秒，归零后验证 30 秒，通过后请求保存 |
| imu cal cancel | 取消标定/验证，必要时尝试退出标定模式 |
| imu stream on/off | 调试时开关连续角度输出 |

删除网页 120 秒按钮与命令定义，固件拒绝 `imu verify 120`，底层验证接口也不再接受 120000。原生标定后的 30 秒属于流程内部验证，未缩短。

`imu verify 10` 暂留兼容别名，现有“准备跑图”使用它，不增加第二套行为。`imu cal clear` 暂留 cancel 的兼容别名，`imu cal forget` 保留原拒绝说明，均从公开帮助中隐藏，避免旧手动收藏产生意外动作；不擦除存储。新界面不再提供冗余入口。

同步更新入口/协议模块资源版本，保留用户收藏原始文本。旧收藏中的 120 秒命令会被新固件拒绝，不静默改写成其他操作。
