## 当前接线与配置

表中 TX/RX 均从 **STM32** 视角描述，连接模块时 TX 接模块 RX，RX 接模块 TX。

| 用途 | 外设 | STM32 引脚 | 当前程序配置 |
| --- | --- | --- | --- |
| Zigbee / 调试控制台 | USART1 | PA9 TX、PA10 RX | 115200、8N1，单字节中断接收 |
| 激光雷达，暂不使用 | USART2 | PA2 TX、PA3 RX | 保留 115200、8N1 初始化，未启用雷达业务 |
| 串口屏 | USART3 | PD8 TX、PD9 RX | 115200、8N1，TX DMA，RX 中断 |
| 二维码扫码模块 | UART4 | PC10 TX、PC11 RX | 115200、8N1，单字节中断接收 |
| 步进电机总线 | UART5 | PC12 TX、PD2 RX | 115200、8N1，TX DMA、RX Normal DMA + IDLE |
| 香橙派视觉通信 | USB OTG FS Device / CDC | PA11 D−、PA12 D+ | 核心板原生 Type-C，USB 时钟 48 MHz |
| OLED | I2C1 | PB6 SCL、PB7 SDA | 100 kHz，7 位地址 0x3C |
| HWT101 | I2C2 | PB10 SCL、PB11 SDA | 100 kHz，7 位地址 0x50 |
| 舵机，沿用旧工程 | TIM1 CH1 | PE9 | PSC=167、ARR=19999，50 Hz PWM，初始 CCR=0 |

HWT101 的 SDA 已由作者确认是 **PB11**。I²C 使用开漏引脚，需有外部上拉；本配置没有开启内部上拉。板外信号按 3.3 V 逻辑连接，供电与上拉电压应核对实际 PCB。

嘉立创官方说明确认天空星核心板 Type-C 连接 STM32 USB 引脚，可作为 USB Device 通信口：[核心板说明](https://wiki.lckfb.com/zh-hans/fdb/skystar.html)、[引脚表](https://wiki.lckfb.com/zh-hans/web-tool/fdb-pinout.html)。香橙派一侧需要使用 USB **Host** 口。

USART6 的生成配置仍在文件中，但主程序不再初始化或用它与香橙派通信。PA9 给 USART1 使用，因此 USB VBUS sensing 保持关闭。

## USB 两端协议

USB CDC 在 Linux 上表现为虚拟串口，Python 继续用 `pyserial`。`baudrate=115200` 是 CDC 线路编码参数，不会将 USB 通信转回 UART 引脚。

STM32 → 香橙派，4 字节：

```text
FF B2 Color FF
```

Color：1 红、2 黄、3 蓝、4 绿、5 黑、6 浅蓝。

香橙派 → STM32，14 字节：

```text
FF B2 Color Valid CX_H CX_L CY_H CY_L DX_H DX_L DY_H DY_L SUM FE
```

- `Valid=1` 表示检测有效，`Valid=0` 表示未检测到目标；无效时 Python 发送零坐标和零误差。
- CX/CY 是大端无符号 16 位；DX/DY 是大端有符号 16 位。
- SUM 是下标 1～11 的字节累加后取低 8 位。
- USB 中断只复制收到的字节，主循环解析半包、粘包及校验，筛选当前请求的颜色。
- STM32 的发送函数先检查 USB 是否配置完成和是否忙，再复制到持久发送缓冲区。局部数组退出作用域不会破坏异步发送。
- Python 必须显式指定设备，发送设置 0.2 s 超时，并报告写入不完整。断线后重新运行 Python，再重新发颜色请求；当前没有自动重连。

**B3 差异：**附件 `change.py` 只支持 B2，收到颜色命令后自行进行“粗定位 → 色环精定位”。它没有 B3/0A～0C 的圆环编号算法。`Camera_RingStart` 保留接口但返回 `HAL_ERROR`；旧 B3 标定/对位命令不能与此 Python 配套使用。主程序 PE2 已改为对当前选中颜色调用 B2 物料视觉对位，PE3 仍切换二维码第二组的三个项目。视觉对位需要旧工程要求的参考位置和标定，不能将单独的 USB 通信测试当成运动标定完成。

## 最小联调步骤

1. 用 Keil 的 `template` Target 构建，确认烧录文件来自当前模板目录。
2. 将天空星核心板 Type-C 接到香橙派的 USB Host 口。先查看实际枚举设备：

   ```bash
   python3 -m serial.tools.list_ports -v
   ls -l /dev/serial/by-id/
   ```

3. 将当前 `orange_pi/change.py` 复制到香橙派原视觉环境中，保留已经安装的 OpenCV、NumPy 和 pyserial。用上一步实际设备名替换下面的占位符：

   ```bash
   python3 change.py --usb-port /dev/serial/by-id/实际STM32设备名
   ```

   也可使用实际枚举的 `/dev/ttyACM*` 路径。旧参数名 `--uart-port` 是同一选项的兼容别名；没有默认 `/dev/ttyS6`。多个 CDC 设备时不能仅凭编号判断是哪块板。

4. Python 显示“等待 USB CDC 颜色命令”后，通过 USART1/Zigbee 控制台发送以下 ASCII 命令，以回车结束：

   ```text
   camera material 3
   ```

   这条命令只启动蓝色识别和坐标跟踪，不发出电机位置命令。预期 Python 显示 `FF B2 03 FF`；目标出现时 USART1 控制台输出 `VISION DATA` 和 CX/CY/DX/DY。也可以在主循环业务中调用 `Camera_MaterialStart(CAMERA_COLOR_BLUE)`；遇到 `HAL_BUSY` 或未连接错误，稍后重新请求。

5. 先验证串口屏、二维码与 HWT101 的独立现象，再恢复视觉对位。HWT101 上电后成功应答时 USART1 每 200 ms 输出一次 yaw；断开 I²C 后不应持续将旧角度当成新数据输出。

## 验证结果与限制

本节保留迁移阶段结果；整理后的软件验证和待上板项目以新的三页使用说明为准。

- Keil 全量构建：0 errors、1 warning。日志：`.embeddedskills/build/template-template-rebuild.log`。HEX：`template/MDK-ARM/template/template.hex`，AXF 同目录。
- 旧代码警告来自 `mechanical_arm.c` Z 轴配置 `{2000U, 500U, 0U}`：Acceleration 是 `uint8_t`，500 在原工程中也会截断为 244。迁移保留原参数，需作者后续核对该加速度的真实意图。
- Python 6 项通信/参数测试通过，另有 STM32 Camera 协议、CDC 发送缓冲区及 HWT101 I²C 主机测试通过。覆盖拆包、粘包、校验错误、符号及大小端、无效目标、USB BUSY/未连接、异步缓冲区、启动重试和过期数据。
- Python 已通过语法编译；本机没有 OpenCV/NumPy，未运行真实摄像头识别。识别算法与附件保持一致。
- EIDE 只同步并检查了文件路径，未运行其构建后端。CubeMX 未重新生成代码。
- 尚未烧录或进行真实 USB 枚举、I²C 应答、Zigbee、屏幕或电机上板联调。

HWT101 依据：厂商 [HWT101 手册](https://m.media-amazon.com/images/I/916UMhYqC5L.pdf) 的单 Z 轴、I²C 接口和启动时间说明，以及 [WIT 标准协议](https://wit-motion.gitbook.io/witmotion-sdk/wit-standard-protocol/wit-standard-communication-protocol) 的默认 I²C 地址、Yaw=0x3F 和原始值/32768×180°。实际模块地址及寄存器应答仍需上板核对。
