# 串口免断电恢复四轮同步缓存（2026-10-06）

## 目标和原因

用户要求通过串口解除普通停车中断同步批次产生的运动锁定，避免反复给驱动器断电。原实现中，非零F6/FD同步批次尚未完成即停车，会留下`SyncCacheUncertain`；实际四轮停住并不能证明驱动器未保存旧运动命令。旧`bus recover`只检查总线和电机状态，不处理缓存，因此仍需物理复位。

修改前COM14证据：`cache-recovery-before-flash.log`中四轮实际RPM均0，`chassis task stage=5 error=5 locked=1`，X=82.703 mm；没有将其解释为串口断连或实际驱动故障。

## 实现

沿用`bus recover`/`bus status`，不新增强制unlock命令：

1. 原有停车/取消任务、排空旧应答、ID1～8速度/状态/回零三轮检查保持。
2. ID1～4分别缓存F6目标0 RPM、加速度0、同步标志1，逐条要求Receive应答02。
3. 四条写入均通过后，逐地址发送FF 66同步，逐条要求应答02。**不广播**，避免触发ID5～8的缓存。
4. 重新读取四轮速度/状态/回零信息，沿用既有停稳速度容差≤1 RPM；通过才清除运动锁定。
5. 成功回复包含`chassis_ready=1 chassis_cache=cleared wheels_stopped=1 tasks_resumed=0`。开始新底盘批次或真实总线故障会使旧恢复证明失效。

恢复不自动启动追踪/路线，不修改位置原点、有效参数、追踪局部参考或剩余预算；保留已接收轮位移快照。人工停车可取消恢复，零速写入或同步拒绝/超时、故障和仍转动均保留锁定，处理后可重试。`chassis reset-confirmed`仍只供真实驱动复位后确认使用。

驱动依据：项目内《ZDT_X42S第二代闭环步进电机用户手册V1.0.5》第37页同步缓存、第53页Emm F6零速度及加速度0、第60页FE停止/FF同步和应答格式，以及保留的官方`Emm_V5_Synchronous_motion(addr)`接口。实际同总线地址限定和应答验证由本车代码实现，不修改官方驱动。

## 修改范围

- `Hardware/motor_bus.c/.h`：扩展原恢复状态机，不增加静态缓存或新总线框架。
- `App/mecanum_chassis.c/.h`：以新恢复证明解除同步缓存锁定；物理复位入口保留独立校验。
- `App/arm_console.c`：输出缓存和实际停车证明。
- 网页`terminal-format.mjs`：新增恢复阶段/结果中文翻译，无导航或运动行为改动。
- 测试、协议、工具`Code/tools/verify_bus_recovery.py`和本记录。
- IOC、EIDE、香橙派、雷达、静态取放、驱动默认设置不改。

## 验证

先补测试并观察失败，再实现：旧恢复完成后零缓存/同步/后检查掩码均缺失；旧完成证明可误用于后续取消批次；旧中文解析无法说明清零阶段。修复后覆盖零写入、同步应答拒绝/丢失、实际仍运动、取消后重试、旧证明失效和四轮缓存清理，ID5～8不触发。

首次上板检查已完成零缓存和停稳，却返回`chassis_ready=0`。定位为主循环在控制台消费恢复结果前重新排队停车反馈读取，使旧`Mecanum_RecoveryAfterReset`的“所有owner安静”条件失败。补充实际队列回归，先观察同样失败，再将已验证总线恢复与物理复位入口分开：前者允许正常只读反馈继续，不清反馈位置、不放过新运动或新故障。该中间失败保留在`cache-recovery-hardware.log`，不冒充成功。
