# 底部恢复兼容比赛保留回复（P008）

用户要求修复底部恢复按钮，并明确“修改程序，不编译”。本轮只修改网页恢复逻辑、源码回归与文档；没有调用C编译器、Keil、DAP、串口发送或烧录工具，没有运行会构建C规划器的测试。

## 原因与修改

普通`bus recover`完成输出`OK bus recover complete ... chassis_ready=1 ... wheels_stopped=1`。比赛保留路径先输出`OK bus recover requested mission_preserved=1 tasks_resumed=0`，实际完成由比赛报告`OK grab route state=paused ... stop_confirmed=1 ... reason=bus_recovered ... auto_resume=0`；原网页只等待普通完成报文，因此比赛已经恢复也会等待25秒后超时。

- `stop-recovery.mjs`继续支持普通完成格式；比赛路径只接受本次命令回显及mission_preserved受理之后的比赛状态，受理前残留状态不参与成功判定。
- 比赛必须同时为paused、bus_recovered、stop_confirmed=1、auto_resume=0；仅受理、重试阶段、尚未停稳或resuming均不宣布完成。成功后再只读查询`chassis task`，确认当前总线error/locked均为0、运动已停止。
- `bus_recovery_wait`直接显示固件的reason，并保留比赛进度，允许用户处理后显式重试；`bus_recovery_retry`继续等待。恢复写入仍只发送一次。
- 随后沿用当前停车编号解锁、反馈准备所有权、四轮新鲜静止反馈及定位核验。新的停止、断线及连接代次变化仍取消待办，迟到成功不会解除新停车锁。
- 比赛成功提示“比赛保持暂停，请在比赛卡片显式继续”。定位参考无效时提示处理参考问题，不自动归零、回零、建立测试原点或发送continue。
- 本轮未改固件协议、Python服务、恢复期限、轮询周期或运动控制。已有其他对话的工作区修改保留。

先补回归，旧网页面对实际比赛失败回复`state=bus_recovery_wait reason=motor_disabled`，仍等待25004 ms并返回通用超时，未返回具体原因，用例失败；修复后即时返回motor_disabled。

恢复专项16项全部通过，包含6项新增比赛场景：正常完成、受理/重试/未确认停稳不提前解锁、失败原因、受理前旧快照、新停止及迟到成功、比赛成功后当前底盘仍锁定。原普通恢复、短暂缺反馈、写入不重放和断线检查保留通过。

连同bridge、比赛恢复状态及主页面模拟共106项Node检查通过、0失败；日志`.embeddedskills/tests/p008-web-recovery.log`。这些直接执行JavaScript源码，不构建或运行固件。同步AGENTS、网页README、连接与恢复手册、底盘协议及P008状态；历史审查记录不改写。
