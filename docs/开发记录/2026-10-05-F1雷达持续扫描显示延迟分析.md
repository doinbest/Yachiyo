# F1雷达持续扫描显示延迟分析（2026-10-05）

## 1. 本轮现象与结论

用户已确认：上一轮修复后，障碍物识别准确。但持续扫描时，移动障碍物需要等待几秒才在网页显示，路线又比障碍物晚几秒出现。

主要瓶颈是USART1无线结果回传及分页调度，不是F407收到障碍后又等待几秒才开始规划。源码在发布完整圈结果之前，已经完成该圈障碍判定与路径规划；网页随后分开下载地图和路径，收齐后分别显示。

本轮只分析并记录原因，未实施降延迟修改。识别准确不代表显示延迟已经解决。

## 2. 分析范围与当前数据流

- 雷达通过USART2，以921600 / 8N1向F407发送数据。
- F407按F1规则处理完整圈，生成障碍格、统计与路径。
- USART1通过DL-20无线链路，以115200 / 8N1连接电脑。
- 本文针对网页雷达建图的 `f1_host` 持续模式，不涉及实车监控或运动控制。
- 正常回传重点是障碍地图、路径和少量预览；完整原始点云仍为按需诊断，不是持续自动上传整圈点云。

当前同步顺序：

```text
F407完成一圈建图与规划
  → 冻结同一版本的地图/路径，通知网页结果可读
  → 网页逐页读取地图，收齐后显示障碍
  → 网页逐页读取路径，收齐后显示路线
  → 网页发送 radar host ack <plan>
  → F407发送一圈最新点云预览
  → 通知下一份最新建图结果
```

下载期间雷达仍继续采集、处理新圈；冻结的是供网页读取的结果，不是让雷达停扫。下一次同步跳过积压的中间结果，不要求逐圈补传。

## 4. 延迟来源

### 4.1 32字节发送后等待30ms，限制了持续输出

当前控制台定义 `CONSOLE_TX_CHUNK_BYTES=32`、`CONSOLE_TX_GAP_MS=30`，每块DMA发送完成后再等待间隔。

115200 / 8N1的纯串口理论上限为11520字节/秒。但按当前分块节奏估算：

```text
单块串口时间 = 32 × 10 / 115200 ≈ 2.78 ms
理论持续输出 = 32 / (30 ms + 2.78 ms) ≈ 976 字节/秒
```

因此提高网页刷新频率，不能消除这部分回传耗时。这里的976字节/秒是MCU发送节奏的理论估算，不是DL-20无线净吞吐实测值；额外命令、状态回复、无线周转和调度还会占时间。

### 4.2 分页有效负载小，逐页往返累积

每页重复携带版本、配置、会话、scan/map/plan、page/pages/offset/total等JSON字段。当前41路点路线约占2903字节、12页；117点预览的点记录本体约468字节，包装后却约3239字节、13页。

网页拿到并校验上一页后才请求下一页。每页的请求、排队和返回累积起来，使路径同步明显长于单纯串口字节发送时间。现有证据不能把全部额外耗时归因于DL-20内部缓存。

### 4.3 地图先显示，路径后显示

网页明确先读取地图，再读取路径。因此地图收齐时就能显示新障碍，但匹配的路径尚未收齐，形成“障碍先出来，路线再等几秒”的现象。

`radar_scan.c` 的 `publish_live()` 在发布完整圈编号与状态前调用 `RadarHostMap_Finish()`。这证明该圈规划在结果发布前完成，但本轮没有测量规划函数的实际CPU耗时。

### 4.4 可靠同步与预览占用下一轮更新窗口

上一轮为解决分页混圈、快照身份变化及末页补读问题，冻结地图/路径，收到网页ACK后才释放。这个机制保证同一组结果可以完整读回；不能为了提速直接取消，导致旧问题重现。

ACK之后又优先发送一圈完整预览，才通知下一份结果。预览约占3秒，是当前更新周期的一部分。物体若刚好在已冻结结果之后移动，会等到下一轮结果同步；10～12秒通知间隔不等于雷达每10秒才扫描一圈。

## 5. 后续优化方向（尚未实施）

在保留115200、F1判障/规划规则及其他控制台功能的前提下，优先优化通信量和调度：

1. 压缩地图/路径包装，减少重复身份字段，提高每包有效负载；保留同版本结果配对与必要校验。
2. 减少一页一次请求的往返，优先连续回传地图与路径，缩短同圈障碍和路线的显示时间差。
3. 降低点云预览的发送频率或占用，避免每次结果后都用约3秒预览阻挡下一份重要结果。
4. 最后再评估32字节/30ms节奏：先核对DL-20手册及实测丢包情况，不能把30ms说成厂商必需值，也不在没有依据时直接取消。

验收应分别记录物体移动到障碍显示、障碍显示到匹配路线显示、相邻完整结果更新时间，并检查连续更新、分页完整性、短时丢包后的恢复及停车回复。提速不得改变障碍判定结果或以旧路线冒充新路线。
