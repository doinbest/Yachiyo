# 工创开源项目 HWT101 零偏校准源码核查

核查日期：2026-09-12。仅分析源码，没有修改本车固件，没有向实物发送指令。

## 结论

用户提出“先检查 HWT101 模块内部零偏校准”的方向应当优先验证。之前本车的 `imu cal start` 是 STM32 对模块输出角度拟合漂移斜率，再进行外部补偿；保存到 W25Q128 的也是这个外部补偿值。它没有完成用户提供的官方“进入零偏获取—静止等待—恢复正常模式”流程。

本轮从先前参考项目中重点核查了六套直接使用 HWT101 的工程，并补查两套邻近项目。发现两套确实包含 `0x48` 零偏获取实现，其中 `2025GongChuang_AGV` 具有可追踪的启动、22 秒计时、恢复正常模式调用链。其余几套主要做起始角度归零、角度解析和航向 PID。

两个模块都漂移，使共同的配置、校准状态及测试环境成为优先检查对象，但不能仅凭此确定唯一根因。源码能证明作者编写了哪些步骤，不能证明本车模块版本一定相同，也不能替代实物校准前后测试。

## 1. 最有价值的参考：Thirtynine3939/2025GongChuang_AGV

- 核查提交：`f1fbab3605f4941fdc14a13d9380aa48700a4b87`。
- [原始下位机源码压缩包](https://github.com/Thirtynine3939/2025GongChuang_AGV/blob/f1fbab3605f4941fdc14a13d9380aa48700a4b87/程序/下位机/Chassis_v2.0.zip)。本轮实际下载并解压检查，不是根据 README 推测。

压缩包内路径均相对 `Chassis_v2.0/`：

| 文件位置 | 实际行为 |
|---|---|
| `Drive/Source/hwt101.c:23–30` | 分别定义解锁、角度归零、保存、重启、`FF AA 48 01 00` 零偏获取及 `FF AA 48 00 00` 正常模式命令 |
| `Drive/Source/hwt101.c:46–57` | `ZerobiasCal_Start(time)` 发送零偏获取命令，记录起始秒数、等待时间，启动 TIM10 |
| `MY/main.c:71–73` | `BTN_ZEROBIASCALI` 事件调用 `ZerobiasCal_Start(22)` |
| `Drive/Source/task.c:140–198` | 实体按键也能启动或中止校准；完成后有角度归零和 OLED 提示 |
| `Drive/Source/task.c:200–221` | 周期任务检查 elapsedSeconds；到期发送正常模式命令，停止计时并标记完成 |
| `Drive/Source/task.c:104` | 校准计时处理函数实际注册到任务调度表 |
| `MY/main.c:48–49` | 主循环实际运行任务处理和按键扫描 |

其核心流程可以概括为：

```text
用户按键
  → 向 HWT101 发 0x48 = 1
  → 定时等待 22 秒，主循环继续运行
  → 向 HWT101 发 0x48 = 0
  → 标记流程结束，重新设定航向起点
```

这是模块内部校准，不是 STM32 计算 `yaw - bias × time`。普通角度置零 `GyroYaw_SetZero()` 使用另一条 `0x76` 命令，与零偏获取分开。

需要保留的验证边界：

- 校准结束路径没有显式发送 `save_settings`；保存命令出现在初始化配置流程中。不能据此声称此次校准结果已经掉电保存。
- 开始和结束校准函数本身没有各自重新解锁；初始化阶段有解锁。是否需要重新解锁，应以手中版本的协议为准。
- 发送封装额外追加回车换行并延时 200 ms；这是项目作者的封装方式，不应直接作为本车 I2C 写寄存器格式。
- “等待结束”只是流程完成标志，没有计算校准后的静止漂移率，因此其完成提示不是精度验收结果。
- 上电显示等待按键，不能把它描述成每次上电都自动执行内部校准。

## 2. 有内部校准入口但流程不完整：enginer-train

原参考名称为 `lzw1996145/enginer-train`，当前 GitHub 重定向到 `Ycn115/enginer-train`。

- 核查提交：`8f2f08e42ac95fafdfdb0e51af525893c98ff47b`。
- [HWT101 驱动](https://github.com/Ycn115/enginer-train/blob/8f2f08e42ac95fafdfdb0e51af525893c98ff47b/Drivers/Hardware/HWT101.c#L17)。

`HW101_adjust()` 的实际顺序：解锁，等待 1 秒，发送 `FF AA 48 01 00`，连续十五次等待 2000 ms（共 30 秒），再次解锁，等待 1 秒，发送保存命令。

实际调用链：

- `Drivers/Hardware/serial_task.c:273–275`：屏幕命令 `0xC1` 设置 `turn_self_zero_flag`。
- `Drivers/Hardware/control.c:770–774`：该标志触发 `HW101_adjust()`。
- `Core/Src/main.c:144–145`：启动时调用 `HWT101_Init()`，紧邻的 `HW101_adjust()` 调用被注释。

因此它提供的是手动校准入口，不能说每次上电都会校准。

与用户提供的 FAQ 比较，`HW101_adjust()` **缺少显式发送 `FF AA 48 00 00` 恢复正常模式**，不能当作完整标准流程照搬。其他实现问题包括长时间阻塞、未检查 DMA 发送结果，以及函数最后一次 DMA 使用局部数组但未等待完成便返回。

初始化里的 `0x76` 只是角度归零；配置、保存和重启本身不等于获取新零偏。

`imu_init()` 初始化普通串口协议和维特 SDK、注册回调并扫描波特率。`imu_scan()` 从 SDK 缓存换算角度。

容易误解的函数 `WHT101_ANGLEZCali()` 在 `wit_c_sdk.c:503–510` 只做：

```text
解锁 → 写寄存器 0x76 = 0
```

它是 Z 轴角度置零，不是静止等待约 20 秒的内部零偏获取。

SDK 中存在通用 `WitStartAccCali`、`WitStartMagCali` 等函数，`imu.c` 中对应命令分支被注释。不能把多型号通用 SDK 中的加速度/磁场校准函数当成 HWT101 专用零偏流程。

另一个重要调用边界：上游当前 `USER/main.c:91` 有测试用无限循环，位于 `WHT101_ANGLEZCali()` 调用之前。因此其后正式比赛流程不能描述成当前提交上电必然执行。派生项目把角度归零放进 `car_Start` 等启动函数。两者都没有在已查应用源码中形成 `0x48` 零偏获取流程。

这些仓库未实现该流程，不代表作者没有在上位机中预先校准过实物；源码不能证明这件事。

## 7. 对本车的直接含义

当前 `template/Hardware/hwt101_i2c.c` 只有设备探测和读角度，没有给 HWT101 写内部零偏获取模式。`imu cal start`、`corrected` 和 W25Q128 参数保存属于 STM32 外部补偿，不能替代模块内部校准。

应先做一个能区分原因的实物对照，再决定是否保留外部补偿：

1. 分别固定两只模块，在相近供电、上电时长和静止条件下，记录模块原始 yaw 的变化；例如记录 120 秒并计算角度变化/时间，跨 ±180° 时展开角度。
2. 使用与模块固件匹配的官方“自动获取零偏”流程，校准期间全程静止。用户提供的 FAQ 和 `2025GongChuang_AGV` 源码均指向 `0x48=1 → 约20秒 → 0x48=0`。
3. 恢复正常模式后，再记录原始 yaw 120 秒；比较校准前后的漂移率，不用现有外部 `corrected` 作为内部校准效果证据。
4. 根据对应版本协议确认保存要求，再彻底断电重启复测，验证掉电保持。不能只验证 MCU 复位。
5. 模块内部零偏改变后，旧的 STM32 外部补偿值应失效，避免继续自动恢复旧值、形成重复补偿。以后确有残余漂移，再针对校准后的输出评估是否需要额外补偿。

本车使用 I2C2；以上竞赛工程的有效参考是校准时序。`FF AA ...` 是 UART 帧，不应直接塞给 `HAL_I2C_Mem_Write()`。I2C 写寄存器的数据格式、解锁要求和保存步骤仍应依据对应 HWT101 协议确认。

“保存到陀螺仪内部”的合理目标是保存模块自己获取的校准参数。不能把 STM32 拟合出的 `0.11652 °/s` 未经单位、比例、符号和寄存器语义核对就写入某个内部寄存器；这些竞赛实现也没有这样做。
