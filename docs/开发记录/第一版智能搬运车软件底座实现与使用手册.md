## 1. 这一版解决什么问题

这不是可以直接参加比赛的完整程序，而是第一版“软件底座”。它优先解决往届开源代码中反复出现的四类问题：

1. 任务码写死为三色数组，无法表达 2027 赛题的四组三位和六种颜色。
2. 香橙派通信只有简单帧头/帧尾，无法识别乱序、旧数据和传输错误。
3. 主循环直接等待视觉或执行动作，缺少明确的链路和安全状态。
4. IMU 断流后仍可能继续使用最后一次角度控制底盘。

本版新增了：

- 四组三位、颜色编号 1～6 的任务码数据结构；
- 二进制和 ASCII 两种任务码解析入口；
- 连续三帧一致才确认任务码；
- 香橙派 USART1 接收协议和 CRC16 校验；
- USART1 中断环形缓冲，协议解析仍在主循环；
- `WAIT_LINK → WAIT_CODE → READY → SAFE_STOP` 最小任务状态；
- 统一安全停止原因；
- JY61P 数据更新时间和错误统计；
- 底盘运动期间 IMU 数据过期保护；
- PC 端任务码测试和香橙派帧生成工具。

## 2. 这一版明确没有做什么

以下功能没有被伪装成“已完成”：

- 没有编写完整取料、搬运、放置和循环比赛路线；
- 收到 `START` 消息不会启动电机，只增加阻止次数；
- 没有解析 X42S 的位置、到位、报警和堵转反馈；
- 没有把理论时间完成判定升级为电机反馈完成判定；
- 没有依据未提供的 HWT101 实物配置猜测波特率和协议；
- 当前 UART4 驱动仍是已存在的 JY61P 临时验证模块；
- 没有实现目标坐标、圆环、物料或障碍物消息的业务处理；
- 没有实现香橙派 ACK 和 STM32 主动发送；
- 没有设计淘晶驰正式比赛页面；
- 没有选择或驱动激光雷达；
- 没有烧录或进行实车测试。

这样处理是为了先建立能够单独编译和验证的通信、数据和安全边界，避免自动路线在硬件参数尚未确认时误动作。

## 5. 当前软件结构

```text
USART1 RX IRQ
  → OrangePi_Link_Rx_Callback()
  → 只把字节写入128字节环形缓冲

while (1)
  → JY61P_Angle_Get()
  → RobotTask_Process()
       → OrangePi_Link_Process()
       → 长度/版本/CRC检查
       → 任务码三帧确认
       → 更新WAIT_LINK/WAIT_CODE/READY/SAFE_STOP
  → Screen_Check_Process()
  → Chassis_Key_Process()
       → 检查安全锁存和IMU新鲜度
       → 必要时RobotSafety_Stop()
  → 每100ms更新Keil Watch调试快照
```

依赖方向保持简单：

```text
HAL/CubeMX → orange_pi_link、jy61p、Emm_V5
                         ↓
       competition_task_code、mecanum_chassis
                         ↓
              robot_task、robot_safety
                         ↓
                       main.c
```

`orange_pi_link` 不包含比赛动作，`robot_task` 不直接解析 UART 字节，ISR 也不修改任务状态或发送电机命令。

## 6. 任务码格式

### 6.1 数据结构

```text
stage[0][0..2]
stage[1][0..2]
stage[2][0..2]
stage[3][0..2]
```

颜色编号暂按 2027 宣讲材料：

| 编号 | 颜色 |
| ---: | --- |
| 1 | 红 |
| 2 | 黄 |
| 3 | 蓝 |
| 4 | 绿 |
| 5 | 黑 |
| 6 | 浅蓝 |

### 6.2 支持的输入

二进制输入固定 12 字节：

```text
04 05 02 03 02 01 02 05 04 03 01 02
```

对应 ASCII 输入：

```text
452+321+254+312
```

格式要求：

- 二进制长度必须恰好为 12；
- ASCII 长度必须恰好为 15；
- 必须是四组，每组三位；
- 三个分隔符必须是 `+`；
- 每一位必须在 1～6；
- 不会因为一帧合法数据立即覆盖任务；
- 连续三个合法且内容完全一致的候选任务才设置 `valid=true`。

## 7. 香橙派通信协议

### 7.1 物理接口

| 项目 | 当前配置 |
| --- | --- |
| STM32 外设 | USART1 |
| STM32 TX | PA9，连接香橙派 RX |
| STM32 RX | PA10，连接香橙派 TX |
| 波特率 | 115200 bit/s |
| 数据格式 | 8N1 |
| 接收方式 | 单字节中断 + 128 字节环形缓冲 |
| IRQ 优先级 | 抢占优先级 2，子优先级 0 |

必须确认香橙派串口是 3.3 V TTL 电平并与 STM32 共地。不能把 RS232 电平直接连接到 MCU。

### 7.2 帧格式

所有多字节整数使用小端顺序：

| 偏移 | 字段 | 长度 | 说明 |
| ---: | --- | ---: | --- |
| 0 | SOF | 2 | 固定 `A5 5A` |
| 2 | version | 1 | 当前为 `01` |
| 3 | type | 1 | 消息类型 |
| 4 | seq | 2 | 请求或结果序号 |
| 6 | payload_length | 2 | 0～32 |
| 8 | timestamp_ms | 4 | 香橙派单调毫秒时间 |
| 12 | payload | N | 按消息类型解释 |
| 12+N | CRC16 | 2 | 小端，覆盖 version 到 payload |

CRC 参数：

```text
CRC16-CCITT-FALSE
初值 0xFFFF
多项式 0x1021
输入不反转
输出不反转
结果不异或
```

标准字符串 `123456789` 的 CRC 应为 `0x29B1`。

### 7.3 第一版消息类型

| type | 名称 | payload | 当前行为 |
| ---: | --- | --- | --- |
| `0x01` | HEARTBEAT | 当前可为空 | 维持链路新鲜度并计数 |
| `0x10` | TASK_CODE | 12 个颜色编号 | 校验并进行三帧一致确认 |
| `0x11` | START | 当前为空 | 只增加 `blocked_start_count`，绝不启动电机 |
| `0x12` | STOP | 当前可为空 | 锁存远程停止并广播停止四轮 |
| `0x20` | TARGET_OBSERVATION | 待定义 | 当前记为不支持 |
| `0x21` | OBSTACLE_OBSERVATION | 待定义 | 当前记为不支持 |

链路在 1500 ms 内没有任何 CRC 正确、版本受支持的帧后，任务状态回到 `WAIT_LINK`。已经确认的任务码暂时保留，但自动路线尚未实现，因此不会借此继续运动。

### 7.4 帧示例

序号 1、时间戳 1000 ms 的空心跳：

```text
A5 5A 01 01 01 00 00 00 E8 03 00 00 F5 7A
```

序号 7、时间戳 1234 ms、任务 `452+321+254+312`：

```text
A5 5A 01 10 07 00 0C 00 D2 04 00 00
04 05 02 03 02 01 02 05 04 03 01 02 EE E1
```

任务需要发送三次，建议每次使用新序号并间隔 50～100 ms，例如序号 7、8、9。

## 9. 最小任务状态

```text
上电
  ↓
WAIT_LINK ── 收到有效帧 ──→ WAIT_CODE
   ↑                           │
   └──── 链路超过1500ms ───────┘
                               │
                  三个一致任务码
                               ↓
                             READY

任意状态 ── STOP/安全故障 ──→ SAFE_STOP
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `ROBOT_TASK_WAIT_LINK` | 尚未收到香橙派有效帧，或链路已经超时 |
| `ROBOT_TASK_WAIT_CODE` | 链路正常，但任务码尚未三帧确认 |
| `ROBOT_TASK_READY` | 已有确认任务码，可以进入下一版的人工启动门禁设计 |
| `ROBOT_TASK_SAFE_STOP` | 已锁存安全停止，当前版本必须复位 MCU 才能恢复 |

第一版没有 `RUNNING`，因为路线、执行机构、X42S 到位反馈和 HWT101 尚未形成可靠闭环。提前加入一个只能依靠延时运行的 `RUNNING` 状态没有实际价值。

## 10. 安全停止

### 10.1 当前停止原因

| 枚举 | 触发条件 |
| --- | --- |
| `ROBOT_STOP_REMOTE_REQUEST` | 香橙派发来 CRC 正确的 STOP 帧 |
| `ROBOT_STOP_IMU_TIMEOUT` | 按键运动期间超过 200 ms 没有新姿态帧 |
| `ROBOT_STOP_CHASSIS_COMMAND_FAILED` | 麦轮解算或航向控制命令提交失败 |
| `ROBOT_STOP_INTERNAL_ERROR` | 进入全局 `Error_Handler()` |

`RobotSafety_Stop()` 的行为：

1. 保留第一个停止原因；
2. 记录停止时间和请求次数；
3. 设置软件停止锁存；
4. 若电机总线已经完成初始化，调用 `Mecanum_Stop()`；
5. `Mecanum_Stop()` 向地址 0 发送 X42S/Emm_V5 广播立即停止帧。

需要注意：当前底层厂家函数返回 `void`，所以这里能证明的只有“软件已调用停止发帧函数”；无法确认 UART5 DMA 是否接受这次请求，更不能证明四台驱动器已经收到并停止。后续必须让底层发送接口返回状态，并接入电机响应、速度/位置和报警反馈。

### 10.2 IMU 新鲜度

`JY61P_Angle_t` 新增：

```text
last_update_ms
```

底盘按键测试的当前规则：

- 从未收到有效角度帧：忽略方向按键；
- 最近有效帧年龄超过 200 ms：忽略新运动请求；
- 运动中超过 200 ms：广播停止并进入安全锁存；
- 校验错误不会更新时间，因此错误帧不能维持“健康”状态。

200 ms 是第一版保护初值，必须根据最终 HWT101 输出频率、主循环延迟和实测丢帧情况重新确定。

## 13. 建议的无电机验证步骤

先不要接电机或把底盘架空，只验证数据链：

1. 编译工程，不烧录时只确认 `0 errors / 0 warnings`。
2. 如需烧录，先确认具体调试器、目标芯片和供电；本次交付没有代为烧录。
3. 用 3.3 V USB-TTL 连接 PA9、PA10 和 GND。
4. 复位后观察 `robot_task_status.state`，应为 `ROBOT_TASK_WAIT_LINK`。
5. 发送一帧心跳，应进入 `ROBOT_TASK_WAIT_CODE`。
6. 发送一帧任务码，任务仍应无效。
7. 连续发送相同任务码三帧，`task_code.valid` 应变为 `true`，状态进入 `READY`。
8. 发送一个颜色为 7 的任务帧，`rejected_task_count` 应增加，已确认任务不被覆盖。
9. 破坏任一 CRC 字节，`crc_error_count` 应增加，任务不变化。
10. 发送 START，`blocked_start_count` 应增加，所有电机保持不动。
11. 发送 STOP，进入 `SAFE_STOP`；如果电机已接入，则会请求广播停止。

前十项全部符合预期后，再进入带电机验证。

## 14. 建议的架空底盘验证步骤

1. 确认 X42S 通信版本、固件模式、地址、115200 配置、校验方式和响应模式。
2. 四个轮子离地，夹爪和其他执行机构保持安全位置。
3. 确认 UART4 当前连接的确实是与 JY61P 驱动兼容的模块；HWT101 未确认前不要直接连接并认为协议相同。
4. 等待 `jy61p_angle.update_count` 持续增加。
5. 轻按一个方向键，观察轮号和方向。
6. 运动中断开 IMU TX，200 ms 后应进入 `ROBOT_STOP_IMU_TIMEOUT` 并请求停止。
7. 复位后重复一次，检查停止原因是否稳定、是否存在继续旧动作的情况。

在 X42S 到位和状态反馈接入前，不进行地面自动路线测试，也不把理论 1 m 结果当作完成判定。

## 16. 下一版优先级

建议不要立刻写完整比赛路线，按以下顺序继续：

1. 确认四台 X42S 的通信板、固件模式、校验和响应方式。
2. 为 UART5 增加明确的帧解析和每台电机状态结构。
3. 用实际位置、速度、到位和报警替换理论时间完成判定。
4. 获取 HWT101 对应手册和实物配置，建立独立 `hwt101.[ch]`，再替换 JY61P 临时模块。
5. 为香橙派增加 STM32 ACK/结果发送以及请求序号对应。
6. 定义 TJC 正式页面控件名称，显示任务码、链路、IMU、电机和停止原因。
7. 在上述反馈全部成立后，增加最小自动状态：只完成“移动到一个测试点并反馈成功/超时”。
8. 最后再增加视觉精调、机械抓取、完整四阶段任务和障碍物规划。

第一版的价值是让后续每个功能都有可追踪的输入、时间、状态和失败出口，而不是提前承诺一条尚未经过硬件验证的比赛流程。
